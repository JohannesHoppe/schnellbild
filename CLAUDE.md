# Schnellbild — project guide & session handover

Read this first. It's the durable memory between sessions. Keep it accurate —
update it when the facts change.

## What this is

A **fast, lean macOS image/video viewer** (SwiftUI, macOS 15+) — "Phiewer but
minimal". Motto: **an image & video viewer that just doesn't suck.** Speed
(also over network volumes) is one part of that, not the headline. It does
what Preview does well: read little, load in parallel, cache via the system,
never block the main thread.

- Repo: <https://github.com/JohannesHoppe/schnellbild> — **public, MIT**,
  © 2026 HAUS HOPPE - ITS (Johannes Hoppe).
- Bundle id: `art.haushoppe.schnellbild`. Current version: **0.12.2**.
- Everything (code, comments, UI source strings, docs, commits) is in **English**;
  the UI is translated (see Localization). The user converses in **German**.

**Every format shows (Johannes' rule).** Schnellbild aims to show every picture and every video, whatever its format: that is its strength. A format that turns up and doesn't show (as an "other file" or not at all) is a gap to close, not an accepted limit: first with what macOS draws (ImageIO, PDFKit, AVFoundation, AppKit) or a preview the file carries inside, then with a decoder from outside (proposed to Johannes with name, version, licence, maintenance, security and App Store fit; nothing is added without his consent, see the global rule on installs). The only exception is a format so rare it is hardly used: then write him an assessment (how common, who makes such files, what showing it would take) and let him decide; never drop one silently. Every format the app shows is listed in the README and on the website (`site/i18n`, all languages); a format added or found missing updates both.

## Architecture & key files

SwiftPM **executableTarget** `Schnellbild` (sources in `Schnellbild/*.swift`).
There is **no Xcode project for the app build**; `xcodegen` generates
`Schnellbild.xcodeproj` (gitignored) **only for the XCUITests**, from `project.yml`.

- **`BrowserModel.swift`** — `@MainActor ObservableObject`, the single source of
  truth. Holds `entries`/`allEntries`, `selection`, `mode` (.grid/.detail),
  `zoom`, `rotation`, search (`searchText` → `didSet` runs `applyFilter`;
  `searchFocused`, `isSearching`, `isFiltering` = non-blank query), history
  (`backStack`/`forwardStack` of `Location` = folder + query + selection +
  finished results, capped at `historyLimit`), `renameTarget`, `showInspector`,
  `showHelp`, sort, `activePlayer` (`PlaybackControl`, AVKit or VLCKit). `showInspector` (`ShortcutAction.info`: I and ⌘I in the grid, list, full view and slideshow, ⌘I also on Actions → Get Info through `menuShortcut`; Get Info in tiles' and rows' menus: `getInfo`) shows `InspectorView` beside the pane's content for `inspectedEntry` (the item on screen, else the one selected).
  **The pane's key bindings live in `handleKey(_:command:) -> Bool`** with the
  `KeyInput` enum — the unit-tested dispatch, always with Schnellbild's own keys; the window's (D, ⌃O, Tab, F5,
  F6, ⇧⌘C, ⇧⌘M) in `WindowModel.handleWindowKey`, and F9, F10, ⌃⌘F in the key monitor
  (`ContentView`). The keys the user set (`Shortcuts.swift`, see below) are resolved before them. Keys typed in the search field go through
  `handleSearchFieldKey` (fixed: they are the field's).
  - Search is **always recursive** and matches **folder and file names**: local
    matches at once, then `recursiveMatches` streams batches (`AsyncStream`)
    from a tree walk; debounced via `searchDebounce`. Each search is a
    `SearchRun` (results, the walk's task, the changes made during the walk,
    replayed on a late batch when they came after the batch began: `ChangeClock`, `SearchBatch.stamp`; what moves out of the searched folder leaves the results); streamed batches are merged into the sorted list (`EntryOrder.merged`), not sorted anew; the model shows one (`search`), the history may hold more. A change below the folder of a search on screen (the other pane copies into it) searches only the changed folders (`refresh(changed:)`, `searchArrivals`); the folder's listing is read again once the search is cleared. Names match through `NameMatcher` in the mode beside the field (`searchMode`, per pane, remembered; `SearchModePicker`): ignoring case without the language's rules (Turkish "I" would miss "img"), the case as typed, or an ICU regular expression (one that doesn't compile matches nothing, no walk; matched off the main thread, the folder's own items too (`NameMatcher.isCostly`, `matching`), giving up on a name after `regexTimeLimit` through ICU's progress callback, and on every name once the search is over: `matches(_:stop:)`). A `SearchRun` keeps its matcher; history reuses a run only for the same query and mode.
  - **`FileChange`** (`.moved` / `.removed`) is the one mechanism for changes
    the app makes on disk: `apply(_:)` runs it over every list the model holds
    (folder entries, search results, pending selection, history, the slideshow's items) and keeps
    the selection. Rename and trash only create the change. A batch is looked up by path (`FileChanges`: each entry through its own folders, not through every change), so trashing or moving thousands stays fast.
  - **Changes outside the app** (the Finder, a camera import, another Mac on a share): `relist` reads the folder shown again in place and `merge`s it (what went is applied as `FileChange.removed`, so results, history, marks and the slideshow follow; what came or changed is merged in where it sorts; selection, marks, search and scroll position stay; while searching, `searchArrivals` finds what matches). Without `force` it reads only when the folder's date differs from the one taken before the listing (`listedStamp`, one look off the main thread; no date, as on a share slow to answer, leaves it as it is). Triggers: FSEvents (`FolderWatch`, one per pane on the folder shown, `watchesFolder`, on for the app's panes through `watchFoldersByDefault`, not inside archives: changes in the folder relist it, changes below it make the tiles around them read previews and emptiness again (`forgetBelow`) and a search look there, `dropVanishedResults`; the folder itself moved or deleted opens the nearest folder still there, `followFolderGone`, looked for only while none of the app's own changes is under way, `transfersUnderWay`, each counted until its `FileChange`s are applied: FSEvents may report the folder shown gone during the app's own rename of it, which the pane follows instead); the app or a window becoming active (`DiskEvents`: every pane of every open window, for what FSEvents doesn't report, such as other Macs' changes on a share); a volume unmounted (`volumesChanged`: a pane on it goes to the drives' level, one at the drives' level relists; mounting too); View → Reload (⌘R, `reload`: every tile's previews forgotten, a search searched again; inside an archive a new `load`).
  - A listing (`listing` → `FolderListing`) has the grid's entries and `otherFiles`: every other file (not hidden unless hidden items are shown, see `HiddenFiles.swift`; not a later volume of an archive shown, packages included), listed by name under the grid (`OtherFilesList`) and counted in the status bar, so a folder with only such files never reads as empty. They aren't selectable; their rows (`OtherFileInteractions`, grid and list) have a context menu (rename: `beginRename(_: OtherFile)` → `renameFileTarget` → `RenameView(file:)`; reveal; trash) and drag like tiles; `applyHere` keeps `otherFiles` in step with every `FileChange`. A folder or archive that can't be listed sets `loadError` ("This folder / archive can't be read" with the system's reason), never "This folder is empty". Labels say exactly what is and what happens (no prose): check them when adding UI text.
  - ↑/↓ in the full view and slideshow (`verticalKey`): on a video the volume of every video in tenths (`changeVolume`, remembered, `PlaybackControl.setVolume`, shown by `VolumeDisplay` a moment); on a zoomed-in picture a fifth of the view further up / down (`panRequest`); otherwise nothing — paging is ← → / ⌘← ⌘→ only. Videos: ←/→ jump 10 % of the length (`skim`), ⇧←/⇧→ 1 % (`fineVideoJump`, `fineSkim`, staying in the video); a video left and come back to in the same folder goes on where it was (`PlaybackPositions`); `VideoProgressBar` under the position badge reads `activePlayer.progress` four times a second.
  - Sorting is `EntryOrder` (what it compares worked out once per entry, `Keyed`; names as the Finder compares them, `localizedStandardCompare`). By distance (`SortKey.distance`, `ShortcutAction.sortDistance`, ⌘6 unless changed; `ShortcutAction.sorts` holds one action per `SortKey`, in its order): from `distanceOrigin` (per pane, remembered as `distanceOrigin` in the preferences; set by `setDistanceOrigin` from an item's place, `sortByDistance(from:)`, which alerts through `locationMissing` when it has none, or from the sheet `DistanceOriginView`, `distanceOriginRequested`, which also opens when Distance is chosen without an origin); the places (`locations`) are read only while sorting by distance (`readLocationsIfNeeded`, from `entries`' didSet like the capture dates, so search results from subfolders too), 64 files a step through `LocationCache` (eight at a time, off the main thread), sorted again after a step at most twice a second; more than one step shows `locationProgress` in the status bar; another sort or folder stops it (`stopReadingLocations`). Items without a place go last in either direction; folders keep their group. Not inside archives (as for date taken). The list shows a Distance column and tiles a tooltip while sorting by distance (`knownDistance`, `GeoPoint.describeDistance`: km or mi by region). A list longer than `mainThreadSortLimit` (5 000) is sorted off the main thread (`ordered` in `load`, `resort`), again when the order or the lists changed meanwhile (`orderRevision`, `listRevision`); shorter ones at once. Changes on disk are followed in place (`EntryOrder.following`: what stays keeps its position, what moved is merged in where it now sorts), as are streamed results and a new folder (`merged`).
  - Paths are compared with `canonicalPath`: pure string work (standardized,
    `/private/var` → `/var`), no file system access, because it runs per entry
    on the main thread and must stay fast on network volumes. Each `GridEntry` carries its own (`GridEntry.canonicalPath`, worked out when it is made); `index(ofPath:)` finds an entry in `entries` by it, the second lookup after a change of the list making a map by path for the lookups after it.
  - `open(folder:)` records history; `navigateBack/Forward` restore folder,
    query, selection and the search (`SearchRun`: results, the walk, changes
    to replay). A search still running when the user leaves keeps running
    in the history (the newest `backgroundSearchLimit`; older ones stop and
    are searched again on return), so "Back" shows it without starting over.
    The stop button (`stopSearch`) ends a walk and keeps its results.
  - Moves and copies into folders (`move(_:into:how:)`: drops, F5, F6) are decided on the main thread (conflicts ask: Keep Both / Skip / Cancel, which stops the whole move, and "Apply to all" when more names are taken: `askKeepBoth` → `ConflictAnswer`, `planMove`) and carried out off it (`FileActions.run`, the live ones through `LiveFiles`; a test's spy inline); `transfersRunning` shows in the status bar, and `finishMove` applies the result: per item a `TransferOutcome` with the files done (a split archive's first parts also when a later one failed: their `FileChange`s and Undo) and the one that failed, reported together (`TransferFailure`). A copy (`LiveFiles.copy`, also a move to another volume, which then removes the original) is written under a hidden temporary name in the target folder (`.schnellbild-copy-<UUID>`, `isPartialCopy`) and renamed once complete, never over a name taken; on failure it is removed, and a listing removes leftovers of that exact pattern that this process isn't writing (`PartialCopies`) and that haven't changed for 12 hours (another Mac may be copying into a share); one it keeps is a hidden item like any other (listed while hidden items are shown). Moves on one volume are renames.
  - New folder (⇧⌘N, `beginNewFolder` → `NewFolderView` → `createFolder`): nothing is made until the name is confirmed; the folder is added to the listing and selected. Tiles drag (`TileDrag`: the file for the Finder, plus an own-process type so the window's drop zones stay away) onto a folder tile or `..`: `move(_:into:)` moves on the same volume and copies to another (`FileActions.transfer`), applies `FileChange.moved`, and drops what left the folder from its listing. Not in archives.
  - Renaming a folder or file (`rename`, also from the full view; a file must keep a media extension) never navigates: folder, query and
    results stay; the folder and everything listed inside it get the new path
    (`FileChange.moved`), as do history entries and results still streaming in.
    `FileActions.conflicts` refuses a target that is a different item (also
    the case-variant on case-sensitive volumes such as NAS shares); the live
    case-only move is one system rename (`LiveFiles.renameCase`: `renamex_np` with `RENAME_EXCL`, else `rename` when the name taken is the item's own), and only a volume that does neither gets a hidden temporary name carrying the new one (`.schnellbild-rename-<UUID>-<name>`), rolled back on failure and put back by a listing if the app ended in between (`restoreIfLeftOver`, after 60 s at rest; until then a hidden item like any other). Renames count in `transfersUnderWay`, so quitting waits for them.
    The grid behind a slideshow or the tour (`presenting`) doesn't move: `canGoBack` / `canGoForward` / `canGoUp` are false, Back, Forward and Enclosing Folder do nothing, the menus' navigation, search, bookmarks, file actions and sorting are disabled, and the slideshow takes ⌘↑ / ⌘↓.
    ⌘↑ / `..` = enclosing folder (`goToParentFolder`; above "/" the drives' level `/Volumes`, nothing above that: `parentFolder`, `isDrivesLevel`; drives show an icon and are never read for previews or emptiness, `FolderTile.driveImage`, nor renamed, moved or trashed, `isDrive`, `canChange`; `com.apple.*` mounts are left out); Backspace is Back (`leaveDetailOrGoBack`: out of the full view, else `navigateBack`, with no history the enclosing folder).
  - Side effects (Finder, open, trash + confirm alert (one name: "Move “x” to the Trash?"; several: counted through `Localizable.stringsdict`, the names below), move/rename) go through
    the injectable `FileActions`; tests pass a spy. `--ui-testing` makes the app
    use its own `UserDefaults` suite (`--reset-state` clears it, once per launch: `makeDefaults` is asked again by `Shortcuts`, `Bookmarks` and the quit).
  - As in the Finder, Space opens the selected item and Return renames it (`beginRename`; on `..` both go up); in the full view Return goes back to the grid, in the search field it opens the selected result.
  - ⌘⌫ / ⌘↩ return `false` from `handleKey` so they reach their menu items
    (the local key monitor sees keys before menu key equivalents). While a
    text field is edited the monitor hands them to the field editor instead
    (`ContentView.textFieldTakes`, also ⌘ with an arrow), so they edit the
    text. Keys with ⌥ pass untouched except ⌥← / ⌥→ (turn the picture, `handleKey(option:)`); keys with ⌃ pass untouched, except ⌃⌘F (full screen, through
    `FullScreenSwitch`) and ⌃O (the dual pane). On a layout without Latin
    letters a letter key is read as on the user's Latin layout (`LatinKeys`).
  - Packages (`.photoslibrary`, `.app`) are single items, as in the Finder:
    `entry(for:keys:)` drops them, so listing, search and slideshow never
    walk into them (`containsMedia` skips them too); one dropped, opened with `--open=` or saved as the last folder opens its folder with it selected (`isPackage`). Symbolic links count by what they point to: a link to a folder is an entry at the link's own URL (trash, rename, move, marks and the tile's id act on the link, as in the Finder) with `GridEntry.linkTarget`; opening it, its previews, emptiness, bookmark, slideshow and drops go to `browseURL` (on `/Volumes`, "Macintosh HD" → `/` stays a drive). A link to a file must lead to the same media kind, one named like an archive to an archive of the same format and extension. The slideshow's walk doesn't follow links (`isLink`), nor do the enumerators, nor a search's `FolderFacts`.
  - Marking: the ⇧ range starts at `markAnchor`, a path (re-sorts and search batches move items); plain arrows, Home and End reset it. Marks that leave the listing are dropped.
  - Rename, new folder (`renameOnDisk`, `createFolder`) and Keep Both's free names (`TransferProbe.freeNames`) touch the disk off the main thread, the live actions through `LiveFiles`; the Trash prompt waits for an archive's parts to be listed (`trashLookupPending`).
  - SVG is an image like any other. ImageIO can't read it, so the full view
    draws it with `NSImage` (`VectorPicture`, in `FullImageView.swift`) at
    the view's size, larger when zoomed in; QuickLook makes its tiles and folder previews, and where it gives the icon or nothing the app draws them the same way (`ThumbnailCache.pictureThumbnail` → `VectorPicture.render`). PDFs are vector pictures too (ImageIO reports no size for them), drawn by PDFKit (`PDFPages.swift`) page by page in the full view, like a video's seek: `skim` on a PDF turns its pages (`showPDFPage`; each page at fit and upright, zoomed, panned and turned on its own), before the first and after the last page `page` goes to the previous / next item (not with a key held down, as at a video's ends), so the actions `fullPrevious` / `fullNext` (← →, as in Phiewer ⌘← ⌘→, or the user's keys) turn pages and `fullPreviousItem` / `fullNextItem` leave at once; ⇧← ⇧→ (a video's fine steps) do nothing. The page on screen is `pdfPosition` (url, page, count), set by `FullImageView` once the PDF is open (`pdfOpened`; the same PDF again keeps its page), cleared by `resetTransforms`, so a PDF shown again starts at its first page; a PDF not open yet is left with ← → like a picture. Only in the full view (`pagedPDF`): the slideshow shows a PDF as one item, its first page. The badge adds "Page 3 / 12", the mini keyboard has its own row (`MiniKeyboard.Context.pdf`), tiles and the Inspector show the first page (`VectorPicture` → `PDFPages`).
  - Full screen goes through `FullScreenSwitch`: a request during the
    window's animation (an empty slideshow ending at once) is carried out
    when it ends, each window on its own (its animation, its waiting request). Window actions use `BrowserModel.appWindow` (the main
    window; the key one can be the Adjustments popover).
- **`DualPane.swift`** — `WindowModel`: each pane's `onFileChange` hands its `FileChange`s to the other pane (`adopt`: its lists, history and the folder shown follow a rename, move or trash); only the active pane's changes reach the window's views and menus. the window's one or two panes (`left`, `right`, each a `BrowserModel`; the right one keeps its own last folder and sort through `settingsPrefix`), `active` (Tab), `dual` (D, ⌃O, remembered), `split` (the left pane's share of the width, dragged on `PaneDivider` in `ContentView`, remembered; double click: half; `PaneDivider.leftWidth` lays them out, `pane(atX:width:)` finds the pane under a trackpad pinch), `sendToOtherPane` (F5 or ⇧⌘C copy / F6 or ⇧⌘M move the active pane's `actionEntries` into the other's folder; refused with `SendRefusal` while the other pane shows search results, as drops are; ⇧⌘C / ⇧⌘M because the F-keys need fn on a Mac keyboard: ⌘C / ⌘M stay Copy and Minimize, ⌥⌘M is Minimize All, ⇧⌘C / ⇧⌘M are free in the app and in macOS), `handleWindowKey` (the window's keys before the pane's). A pane's `onFoldersChanged` makes the other pane `refresh()` when it shows a changed folder; volume and mini keyboard are kept in step. Tiles dragged over a pane where they would land in its folder (`paneDropFolder`: free space and bars via `PaneDrop`, non-folder tiles via `FolderDrop`) set `dropIntoFolderTargeted`: `PaneDropHint` outlines the pane and names the folder. A move leaves out what is gone since it was dragged or marked (`TransferProbe.gone`, lstat in the look off the main thread; it stays beside `TileDrag.byTheUser` below, since F5 / F6 hand over marked items without a drag, which the Finder or another Mac may have moved meanwhile): on CI (macOS 26) a tile dragged into the other pane was now and then dragged and dropped a second time, its `onDrag` called again about a second after the first drop without a mouse down the app saw, and that second move asked whether to keep both copies of the file the first had moved, a modal alert that took the next keys. Such a drag starts with no mouse button held (CI test log: `drag [b.jpg] buttons=0`, before the mouse came up), so a drag carries something only while the left button is held (`TileDrag.byTheUser`, through `TileDrag.provider` in the tile, other file and playlist drags): otherwise its drop would move the file again once ⌘Z has brought it back (`testRenameNewFolderAndMoveAreUndoneAndRedone`). The drop comes before the app has the press's last drag events and its mouse up (CI test log: `drop into the pane` 0.5 to 1.3 s before `mouse up`); that second drag began on one of those events, 2 ms before the mouse up came, and its session, waiting for a mouse up that had already come, took every key until Esc (`testTheDualPane`: D after the drop reached no key handler). So once a drag of the user's has begun (`TileDrag.provider`), its press's drag events with the button already up are left out (`TileDrag.start`, a mouse monitor; with `--test-log`: `drag event after the drop left out`). `NortonMenus`: F9 (the app's menus in the window), F10 (quit after asking). Marking (`BrowserModel.marked`: ⌘-click, ⇧-click, ⇧-arrows, ⌘A, Insert or M (Mac keyboards have no Insert; ⌃Space is the input source switch); Esc unmarks) feeds `actionEntries`, which trash, F5/F6 and dragging use. Norton Commander's F-keys are a second way next to the Mac keys (F3 open, F4 default app, F6 rename in a single pane / ⇧F6, F7 new folder, F8 trash); where they collide the Mac key wins (F2 renames, not Norton's user menu). Menu titles carry no key hints: keys with ⌘ or ⌃ are real `keyboardShortcut`s (as set, `Shortcuts.menuShortcut`), letters and F-keys are taught by F1 and the mini keyboard. Keys are shown as on Apple's keyboards (⌫ ↩ ⎋ ⇥ ↖ ↘, the space bar by its name in the user's language: `KeyChord.text`; `ShortcutsTests.testKeysAreShownAsOnApplesKeyboards`, `LocalizationTests.testKeyNamesAreGlyphsOrTranslated`); no word appears twice in a mini keyboard row in any language (`testNoDuplicateWordsWithinAMiniKeyboardRow`).
- **Windows (⌘N)** — `WindowGroup(id: "browser")` → `WindowRoot`, one `WindowModel` per window (`WindowModel.claim`: the first window's model, made at launch, for a window while no other shows it; else a new one numbered by the lowest free number, its settings under `window<n>.` and `window<n>.rightPane.`, opening on its own last folder or the folder of the window it was opened from). `WindowAttach` ties the model to its `NSWindow` (`nsWindow`) and calls `windowClosed` (slideshow, full view, search end; the model is `closed`: no other pane's changes reach it and its observers stop (`leaveWindow`), until `claim` takes it again and `reopen` reads its folders afresh). `WindowModel.of(_:)` / `current` (key window, else main): the one key monitor sends each key to the window it was typed in, under `--ui-testing` each window's accessibility identifier is `window.<n>` (its model's number), which the UI tests find windows by; `ModifierClicks` keeps each window's tile frames apart, full screen and slideshows use the pane's `hostWindow`; the menus and Settings follow `WindowFocus.current`. `FileChange`s and changed folders go to every pane of every window. Bookmarks, caches and the slideshow time are app-wide.
- **`ContentView.swift`** — `ContentView` → `WindowView` (toolbar, key monitor, drop zones, mini keyboard, slideshow full screen; works on `window.active`) showing one `PaneView` or two side by side (`pane.left` / `pane.right`, the active one outlined); a `PaneView` is one pane's grid / full view, search bar, status bar and sheets. The status bar's path (`folderPath`: `BrowserModel.shownPath`, the folder's POSIX path, inside an archive the path through it as the app shows it; cut at its start, whole in its tooltip with "Right-click to copy") has a context menu (`pathMenu`, also VoiceOver actions): Copy Path (`copyFolderPath`), Copy Path of Selected Item (`copySelectedItemPath`, not `..`), Reveal in Finder (`revealFolderInFinder`: the folder, inside an archive the archive, nothing at the drives' level); the text goes through `FileActions.copyText`, so tests read it from the spy.
- **`SearchField.swift`** — `NSSearchField` wrapper, always visible above the
  content. It refuses first responder until clicked or ⌘F, otherwise AppKit
  focuses it on launch and it swallows the grid keys.
- **`Bookmarks.swift`** — folder bookmarks (`Bookmarks.shared`, both panes, paths in the preferences, `makeDefaults()` so UI tests keep theirs): ⌘D toggles the folder shown, ⌃1 … ⌃9 open the first nine (`BookmarkItems`: the Bookmarks menu, the toolbar's star `BookmarksButton`), a folder tile's context menu adds / removes; `apply` hands every `FileChange` to `follow`, so a rename or move by the app carries the bookmark along.
- **`FolderWatch.swift`** — `FolderWatch` (an FSEventStream on one folder and below, on a queue of its own, latency 0.5 s, the app's own changes left out (`IgnoreSelf`: they arrive as `FileChange`s), the watched folder itself through `WatchRoot`; more than `namedLimit` folders at once, or events the system dropped, come as nil: read it all again) and `DiskEvents` (unmount / mount, app and window activation). FSEvents reports only changes made on this Mac, also on network shares: the activation relist covers the rest.
- **`Undo.swift`** — `FileHistory` (one per window, both panes; `BrowserModel.undoHistory`): every rename (also the folder shown, from the title bar), trash (`LiveFiles.trash` returns where the item lies in the Trash; an item whose place the volume doesn't say gets no Undo), move and copy (`finishMove`) and new folder (`createFolder`) is recorded as an `UndoStep` of parts, each with the `ItemIdentity` of the item where it lies (volume + file number by `lstat`; a copied or new folder also a hash of its relative paths, `.DS_Store` left out, AppleDouble `._x` files in, read with `HiddenFiles.appleDoubleItems`); `undo()` / `redo()` carry them out off the main thread (`onFiles`), one at a time (`running`; the menu items are disabled meanwhile), only on that very item (another file that took the name, a copied folder something was put into since, a new folder no longer empty: refused, `UndoError`) and never over a name taken meanwhile. Undo Copy and Undo New Folder move the item to the Trash; Undo Move to Trash moves it back out (the App Sandbox allows it: `Spike/TrashUndo`, a Store-entitled probe on macOS 15 and 26 moved files and folders out of `~/.Trash`, also in a later process, and out of another volume's `.Trashes/<uid>` with only a folder there granted). One that can't (the Trash emptied: `goneFromTrash`; the name taken, no permission: `stillInTrash`) says so and leaves the item in the Trash. A failure asks (`FileActions.keepFailedUndo`): keep what wasn't done on top to try again, or forget it so Undo reaches the older steps. The `FileChange`s are applied (the folder shown follows its own rename undone, `followFolder`) and the folders that got something back are read. Shown as Edit → Undo / Redo with the step's name (`UndoCommands`, ⌘Z / ⇧⌘Z, `CommandGroup(replacing: .undoRedo)`; disabled while a sheet is open) and at the top of the context menus (`UndoMenuItems` on tiles', rows', other files' and the free space's). While a text field is edited the key monitor hands ⌘Z / ⇧⌘Z to it as `undo:` / `redo:` (`ContentView.isUndoKey`), so typing is undone there, not a file action. `UndoUITests` drive every Undo and Redo end to end with the real Trash.
- **`BossKey.swift`** — X (not while typing; `BossKey.press`, from the key monitor and `WindowModel.performCommand`) makes every window invisible and click-through (alpha 0, kept open so the app's keys still arrive), hides the app and mutes the players (`BrowserModel.audibleVolume`, `BossKey.changed`). ## Security: files from others

Viewing must never run anything. What is in place:
- Archives are only read, never extracted to disk; entry names are cleaned (`..`, `.`, empty parts dropped; `CraftedArchiveTests.testRarEntryNamesStayInsideTheArchive`, `…Zip…`); symbolic links in them aren't listed. Reads into memory are capped at 256 MB (`ArchiveStore.largestRead`), also for whole files read from disk (`MediaData.read`: SVG, PDF). An archive's index holds at most 1 000 000 entries, the folders their paths imply included (`ArchiveStore.indexLimit`): a header flood can't fill memory; the rest is left out and the archive counts as read in part (`complete` false). `CraftedArchiveTests.testAnIndexStopsAtItsLimit`.
- VLC (`VLCSafety`): every media, the thumbnailer's too, gets one demuxer: the video container its first 512 bytes show (`VLCSafety.container`: Matroska, transport stream at 188 or 192 bytes, MP4, AVI, MPEG-PS, ASF, FLV, Ogg; a recording named `.mkv` that is a transport stream plays), else the one its extension names (a download's in-progress ending left out: `DownloadName`); a file whose bytes show none of these containers and whose extension names no video gets `none` (`VLCSafety.reader`: `.wmv` → `asf,none`, `.flv` → FFmpeg held to its `flv` format), so a "video" that is really an HLS playlist can't make VLC fetch from the network: no reader the content can pick follows a playlist or an address. One demuxer, never a list: VLC treats a demuxer it is told to use as forced, and `ps` / `ts` then take any file, so everything after them in a list would get nothing. `VideoFormatTests` gets a frame from a clip of every listed extension and checks a playlist named like a video, whose segment is a clip on disk, gives none; no subtitle files picked up. Media also get `:no-mkv-preload-local-dir` (else the Matroska reader opens the folder's other .mkv / .mka / .mks files looking for linked segments) and `:no-mkv-use-chapter-codec` (chapter codecs are DVD-style menu programs inside the file). VLCKit reads its libVLC options from the preference `VLCParams` through `UserDefaults.standard`, which also searches the global domain any local program can write; at launch (app and thumbnail extension) `VLCSafety.forgetInjectedOptions` sets the app's own domain to VLCKit's own default list (`VLCSafety.libraryOptions`, copied from `-[VLCLibrary _defaultOptions]` of VLCKit 3.7.5: check it when updating VLCKit) and drops a `-VLCParams` launch argument. Lua is not in the bundled VLCKit and its modules are static.
- AVFoundation: every `AVURLAsset` of a file someone else made (`VideoDetailView`, `ArchiveResourceLoader`) has `AVURLAssetReferenceRestrictionsKey` = `forbidAll`: a reference movie can't make it read other files or the network.
- The media extension's parsers (`MatroskaIndex`, `TransportIndex`) hold times within `MatroskaIndex.largestTime` (Matroska) or the 33-bit clock (transport streams), and the format reader adds and subtracts them saturating (`saturatingAdd` / `saturatingSubtract`), so a crafted duration, time scale or timestamp can't trap; `ContainerTests.testTimesOutOfRangeAreHeldInRange`. File names are logged `.private`.
- Open with Default App (`LiveFiles.openWithDefaultApp`, `openableTarget`): links and aliases are resolved and must lead to a file of their own extension, and only pictures, videos, PDFs, folders and archives of the grid's formats (`ArchiveName.format`) are opened, each with the app for its type; never apps, packages, scripts, installer packages, disk images, xip or Apple archives (they conform to `public.archive` too, and opening them installs or mounts), nor web content (`refusedTypes`). Finder aliases are listed among the other files; a symbolic link counts by what it points to, and a linked folder is listed as the link (trash, rename, move act on it) and opens its folder.
- Other files (`LiveFiles.openOtherFile`, double click / Open in their menu): only documents that hold no program (an allow list of types: text, PDF, office, audio …; a refuse list of types and extensions: executables, apps, packages, scripts, installers, disk images, Terminal settings, Finder locations, and active web content a browser would run: HTML, XHTML, XML, web archives, SVG …; links and aliases resolved first), a .webloc / .url only to an http(s) address, opened with `NSWorkspace.open`. `OpenOtherFileTests`.
- A folder reopened at launch is remembered until the app has run 15 s after its listing is shown (`confirmRestoreLater`, `restoreConfirmDelay`) or quits normally (`restoreUnconfirmed`, per pane of every window; a normal quit clears them all): if the app ended before, the next launch doesn't reopen it (`skippedRestore`), so a file that crashes the app can't crash every launch.
- The app and its extensions run in the App Sandbox (see "One app, two ways out"): no network, no other programs started, only the folders the user opened to it; the release app has the Hardened Runtime (library validation); the thumbnail extension reads only the file QuickLook hands it, also when Finder asks for an MKV's thumbnail; no URL schemes, and document types only as related items (`CFBundleDocumentTypes` with `NSIsRelatedItemType`, role Viewer, `LSHandlerRank` None: sidecars and archive volumes, never offered to open, see `RelatedFiles`); `--open=` and the UI-test switches are command-line only.
- Media Extensions (opted in at launch) run each in its own sandboxed process, and only those the user turned on in System Settings.
- The app itself never goes online: no MapKit, no geocoder. The Mac's position is asked for only when the user clicks Use My Location (macOS asks first; one request) and stays in the app as the distance origin; the privacy policy says so (`site/i18n`, `privacy.stays`). The Inspector's Open in Maps hands an `https://maps.apple.com/?ll=…` address to `NSWorkspace.open` (Apple Maps goes online, the UI says so); coordinates and map links pasted are parsed offline (a short link can't be, and the sheet says why).
- Metadata beside and inside files (`MP4Boxes`, `GPMF`, `XMPMetadata`, `SonyClipXML`, `DJIFlightLog`, `GPXTrack`) is parsed by our own code that checks every size, offset and count and caps what it reads (index 64 MB, XMP 16 MB, clip XML 4 MB, GPX 64 MB, flight logs 128 MB, samples 4 MB); a file beside another is read only when it is a regular file within that cap, checked before reading (`SidecarFile`: a FIFO, a device or a link to `/dev/zero` named like a sidecar is passed over); the XML readers refuse a document type (entities) before XMLParser sees it, and so only documents in an encoding that writes ASCII as ASCII (UTF-8, a declared ISO-8859 or Windows code page; not UTF-16, UTF-7 or EBCDIC, which would hide the declaration from that search: `SafeXML.isASCIICompatible`). Read only, never written. `MetadataSourceTests` feeds them damaged and crafted input.
- The offline map reads only its own files from the app bundle (SHA-256-checked at build time); its readers (`PMTilesArchive`, `VectorTile`, `PlaceIndex`, `Gzip`) still check every offset and length, so a damaged file reads as missing tiles or places (`OfflineMapTests.testBrokenTilesThrowOrReadLessNeverCrash`). The app never goes online for the map; the credit's link opens openstreetmap.org/copyright in the browser. The globe reads only its own files from `Resources/Globe` (SHA-256-checked at build time); `Heightmap` checks the header and the length, the pictures go through ImageIO.
- PDFs (`PDFPages`): read into memory like any picture (`MediaData.read`, the 256 MB cap, also inside archives), opened with PDFKit's `PDFDocument(data:)` (a locked one isn't shown) and only drawn into bitmaps with `PDFPage.draw(with:to:)`; no `PDFView`, so nothing is clicked or carried out: PDFKit's headers name `PDFAction` (go-to, named, remote go-to, reset form, URL) as what a user triggers through a `PDFView` (`performAction`, its delegate's link clicks), and none for JavaScript. Annotations are drawn as they look.
- Remaining risk: the parsers run in the app's process (VLC with FFmpeg, UnRAR, the system's libarchive, ImageIO, PDFKit for PDF, AppKit for SVG), several already while a folder is browsed (thumbnails, archive indexes). A bug in one of them could run code with the app's rights, which the sandbox limits to the folders opened to it, without network. A further step would be a sandboxed XPC helper (read-only, one file) for VLC and the archive readers; VLC's frames are IOSurfaces already, which can cross XPC. Until then: keep VLCKit and UnRAR current with their security releases.

## Offline map data

**Political positions (Johannes' decision, fixed; not to be changed by a data update or an agent):** the map shows the world as the EU and Germany read it, in every UI language.
- **Borders and countries:** Crimea and the oblasts of Donetsk, Luhansk, Zaporizhzhia and Kherson are Ukraine. Kosovo is a state of its own. Northern Cyprus is Cyprus; Abkhazia and South Ossetia are Georgia; Transnistria is Moldova; the Golan Heights are Syria. Gaza, the West Bank and East Jerusalem are Palestinian, the Israeli settlements there included. Western Sahara is a territory of its own (no Moroccan sovereignty). Taiwan is shown as Taiwan. Disputed lines (Kashmir, Aksai Chin, Arunachal Pradesh) are drawn as disputed, and no de facto line of an occupation is drawn as a state border.
- **Names:** renamings by the Trump administration from 2025 on are not followed; places keep the name they had before (the Gulf of Mexico, never "Gulf of America"; Lake Ontario, never "Lake America"; Denali; Fort Johnson in Louisiana). Otherwise the internationally used names (Persian Gulf, Sea of Japan, North Macedonia); in Korean the Sea of Japan carries both names, "동해 (일본해)". Kyiv is "Kyjiw" in German, "Kyiv" in English and every other Latin-script language, "Київ" in Ukrainian; Russian, Japanese, Korean and Chinese keep their names. PS is "Palestine" in each language ("Palästina"; Unicode CLDR's short form), wherever the app names the country, not the system's "Palestinian Territories".
- **How:** `Scripts/build_map_data.py` takes country codes from Natural Earth's countries as Germany sees them and applies a documented overrides section on top (each entry with its source). Natural Earth's German view alone puts East Jerusalem in Israel and leaves the Golan Heights and Northern Cyprus in no country, so `REGION_COUNTRIES` maps regions of Natural Earth's disputed areas (Crimea, the Donetsk and Luhansk areas, Kosovo, Northern Cyprus and the buffer zone, Abkhazia, South Ossetia, Transnistria, Karabakh, the Golan Heights, the West Bank, East Jerusalem, Gaza, both parts of Western Sahara, Taiwan) to their country; a place there takes it first. Borders: a country line near such a region with one country on both sides in this reading (water on one side shows none) is left out (the Crimean isthmus, the Golan's ceasefire line, East Jerusalem's annexation line), and `ADDED_BORDERS` draws Western Sahara's border with Morocco (27°40' N, which OpenStreetMap lacks) as a disputed country border from Natural Earth's shared edge; the build stops if a changed tile would show in more than one place. `PLACE_OVERRIDES`: Kyiv's names, the Palestinian territories' label ("Palestine" per language), Jerusalem has no country of its own (the app takes the photo's: East Jerusalem Palestinian, West Jerusalem Israel), Western Sahara's label (OpenStreetMap: "Sahrawi Arab Democratic Republic", which the EU doesn't recognise either) is "Western Sahara" in every language, Fort Polk, Louisiana stays Fort Johnson (the Army's 2025 renaming). `WATER_NAMES` sets the names of the Gulf of Mexico, Lake Ontario (Executive Orders 14172 and 14422), the Persian Gulf and the Sea of Japan. Country names in the app go through `OfflineMap/CountryNames.swift` (the system's, PS overridden). The place file carries the regions (with Israel's outline after them), and `PlaceIndex.nearby` takes the photo's country from them (else from the nearest locality), counting a place across a border less. In the data as built: Mount McKinley has no label (no peaks), airports aren't in the data. `MapPoliticsTests` pins every case above (e.g. Simferopol → UA, Katzrin → SY, Ma'ale Adumim, Ariel, Modi'in Illit, Ramallah and East Jerusalem → PS, West Jerusalem → IL, Pristina → XK, Kyrenia → CY, Laayoune → EH; Palestine, Kyiv / Kyjiw and the Korean sea label in every language; the Gulf of Mexico's label, no name of a 2025 US renaming in any language; no country border across Crimea, the Golan or inside Western Sahara). When a new map is made, these tests must pass unchanged; a source that disagrees is overridden, the position is not.

OpenStreetMap data from Protomaps' daily build (pinned by date, size and the SHA-256 of its first 16 KiB in `Scripts/map_data.env`; Protomaps keeps a choice of older builds at https://build-metadata.protomaps.dev/builds.json, not all, so a pinned build may disappear; then pick a newer one). `Scripts/build_map_data.py` (Python's standard library only, `python3 -I`) makes `schnellbild-map-<date>.pmtiles` (PMTiles v3, MVT, gzip, zoom 0 to 7: earth, water, boundaries, roads and glaciers from landuse, only the attributes drawn, names only on water label points, 54 MB) and `schnellbild-places-<date>.bin` (the place index: about a million countries, regions and localities from the places of the tiles up to zoom 10, i.e. up to min_zoom 11, names in the app's 20 languages (Protomaps' name:no for nb, name:pt for pt-BR), each place's country code by point in polygon in Natural Earth's countries as Germany sees them (Natural Earth's default draws Crimea in Russia), else the nearest place's; 23 MB; the format is described in the script), and the licence notice `schnellbild-map-<date>-NOTICE.txt`, also written to `Resources/Licenses/OpenStreetMap-data.txt` (committed). The files are not named Protomaps: its README asks forks to use another name. They are published as assets of the pre-release `map-<date>` of this repository (never latest); `Scripts/fetch_map.sh` (called by `fetch_vlckit.sh`, so by `test.sh`, `build_app.sh`, `typecheck.sh` and CI) downloads them into `Vendor/Map` (gitignored), each checked against its SHA-256 in `map_data.env`; `build_app.sh` and `project.yml` copy them into `Contents/Resources/Map`. CI caches them with `Vendor/` (key: the fetch scripts and `map_data.env`).

The inputs are archived with us: the pre-release `map-source-<date>` (`SOURCE_RELEASE_TAG` in `map_data.env`, never latest) holds what the builder reads of the Protomaps build (`directory-z10.json`, the build's header and tile entries up to zoom 10, and the tile data up to the end of zoom 10 as `tiles-<start>-<end>.bin` parts under GitHub's 2 GiB per asset, `SOURCE_DIRECTORY` / `SOURCE_TILES` with their SHA-256) and both Natural Earth zips. `build_map_data.py` fills its cache from there first, each file checked by SHA-256 (downloads resume), and asks Protomaps (after checking its size and first 16 KiB) and naciscdn.org only when the archive can't be reached; `--upstream` skips the archive. So the pinned map can be rebuilt after Protomaps has deleted the build: `python3 -I Scripts/build_map_data.py --cache <empty dir> --check` gives `MAP_SHA256` / `PLACES_SHA256`, whatever the chunks. The place file is the same on every run because the builder takes the places' rows in the batches' order: among a place's copies from one zoom it keeps the first.

To make a new map: set `PROTOMAPS_BUILD`, `PROTOMAPS_URL`, `PROTOMAPS_SIZE` (from builds.json or `curl -sI`) and `PROTOMAPS_HEAD_SHA256` (`curl -s -r 0-16383 <url> | shasum -a 256`) and the new file names, `RELEASE_TAG` and `SOURCE_RELEASE_TAG` in `map_data.env`, run `python3 -I Scripts/build_map_data.py --upstream --extract <dir>` (downloads about 3.8 GB of tile data for zoom 0 to 10 into `build/map-cache/<date>/` in pieces of 256 MiB, resumable, any chunks `tiles-<start>-<end>.bin` already there are used; writes the archive's files into `<dir>` and prints `SOURCE_DIRECTORY*` / `SOURCE_TILES` to pin), publish `<dir>/*` as `gh release create map-source-<date> --prerelease --latest=false` (notes: source URL and date, ODbL, © OpenStreetMap contributors, data via Protomaps, Natural Earth public domain, each file's SHA-256), then run `python3 -I Scripts/build_map_data.py` (a few minutes on all cores), put the SHA-256 it prints into `MAP_SHA256` / `PLACES_SHA256`, publish with `gh release create map-<date> --repo JohannesHoppe/schnellbild --prerelease --latest=false --target <commit> build/map/*` (notes: source build, the commit of the script, the SHA-256 of each file, ODbL, © OpenStreetMap contributors), commit `map_data.env` and `Resources/Licenses/OpenStreetMap-data.txt`. The same input gives the same bytes (gzip without time stamps, sorted output); `--check` fails unless the files match the pinned SHA-256. Without `--upstream` the builder uses only pinned bytes: a cached directory or tile part is used while it matches its pin, a part the archive can't serve is read from Protomaps over the same byte range and held to the same pin, and tile data the pins don't reach stops it. `--self-test` checks that with stand-ins for the archive and Protomaps (`map-data-check.yml`, on every push that changes the script or its pins).

## Globe data

The globe's data is made by `Scripts/build_globe_data.py` (standard library only, `python3 -I`: it reads the OpenEXR star map (ZIP compression, half floats), the TIFFs (LZW for the city lights, Deflate for the satellite picture) and the cloud JPEG (its own baseline decoder) itself and writes the sky, the clouds and the satellite tiles with its own baseline JPEG encoder (T.81: JFIF YCbCr, the DCT in double precision with a fixed summation order, Annex K's quantisation tables scaled by IJG's quality formula, optimal Huffman tables per K.2) and the city lights as a PNG with zlib, so the same inputs give the same bytes, on every macOS; `--check` fails unless all five files (heightmap, sky, city lights, clouds, satellite) match their pins) from the sources in `Scripts/globe_data.env` and published as assets of the pre-release `globe-<date>` of this repository (never latest); `Scripts/fetch_globe.sh` (called by `fetch_vlckit.sh`, so by every build and CI, which caches it with `Vendor/`) downloads them into `Vendor/Globe` (gitignored), each checked against its SHA-256; `build_app.sh` and `project.yml` copy them into `Contents/Resources/Globe`. The notice is `Resources/Licenses/Globe-data.txt` (committed), with the terms of each source beside it (`CC0-1.0.txt`, `NASA-SVS-usage.txt`, `NASA-media-usage-guidelines.txt`: excerpts of NASA's pages with their address and date); credits in the About window, THIRD-PARTY-NOTICES.md and the README.
- **Elevation:** NOAA ETOPO 2022, its 30 arc-second surface elevation grid (CC0 1.0; "not to be used for navigation"; cite https://doi.org/10.25921/fd45-gt74), every fifth sample read through NOAA's OPeNDAP server in eight bands, 3 × 3 of them averaged into cells of 1/8° (each block centred on its cell), whole metres: `schnellbild-heightmap-<date>.sbhm`, 2880 × 1440 int16 (8.3 MB, the format in `GlobeData.swift`). Averaging lowers the summits (Everest's cell about 5 900 m).
- **Night sky:** NASA SVS "Deep Star Maps 2020" (its dark strokes, thin lines and outlines in the source such as near 6h +58°, lifted to the median of the ring of pixels around them: `sky_strokes`) (svs.gsfc.nasa.gov/4851; SVS content is public domain; from Gaia DR2, Hipparcos and Tycho-2), the 4k star map (EXR, pinned by size and SHA-256), tone-mapped (the 99.95th percentile of the brightness white, linear to 0.8, a soft shoulder above) to 8-bit sRGB, a JPEG of 4096 × 2048 at `SKY_QUALITY` 94, 4:4:4 (`schnellbild-sky-<date>.jpg`, 4.1 MB; PSNR 39.6 dB against the tone-mapped picture, largest error 39 of 255; a lossless PNG would be 15 MB, the faint Milky Way is noise to deflate; 4:2:0 smears the stars' colours, single pixels): right ascension 0h in the middle, increasing to the left, declination +90° at the top. The Yale Bright Star Catalogue is not used (HEASARC provides it for research only; Yale keeps the copyright), nor Hipparcos / Tycho / Gaia directly (CC BY-NC).
- **City lights:** "Earth at Night (Black Marble) 2016 Grayscale Maps" (NASA Earth Observatory record 144897), its 3 km GeoTIFF (13500 × 6750, LZW, pinned by SHA-256), reduced by 2.5 to 5400 × 2700 (each target pixel the covered share of 5 × 5 source pixels) as a grey PNG (`schnellbild-citylights-<date>.png`, 0.7 MB, lossless: a grey JPEG is smaller only at quality 90 or less, 0.59 MB), under NASA's media usage guidelines. The credit: "NASA Earth Observatory images by Joshua Stevens, using Suomi NPP VIIRS data from Miguel Román, NASA GSFC" (as the record's page gave it, visibleearth.nasa.gov/images/144897, in the Internet Archive's copy of 2025-11-13; the page itself now redirects to NASA Science's maps page, which shows no credit).
- **Satellite picture:** NASA Earth Observatory's "Blue Marble: Next Generation" (Reto Stöckli), July 2004 without topography (bathymetry shading), the 21600 × 10800 GeoTIFF (Deflate, pinned by SHA-256), read row by row by the script's own TIFF reader, as JPEGs (4:2:0, `SATELLITE_QUALITY` 85, the script's own encoder) in one tile pack `schnellbild-satellite-<date>.bin` ("SBTL", 20.4 MB): `base` the whole Earth reduced 8:1 (2700 × 1350), level 1 reduced 2:1 in 8 × 4 tiles of 1350 px, level 2 the full picture in 16 × 8 tiles (2 km a pixel at the equator, sharp to the flattening zoom). Under NASA's media usage guidelines; NASA asks for the credit "NASA Earth Observatory" (the collection's page on science.nasa.gov).
- **Clouds:** "The Blue Marble" (2002) cloud picture `cloud_combined_2048.jpg` (2048 × 1024, NASA Goddard Space Flight Center, image by Reto Stöckli), decoded by the script's own baseline JPEG decoder (luma) and written grey at `CLOUDS_QUALITY` 88 (`schnellbild-clouds-<date>.jpg`, 0.7 MB). Under NASA's media usage guidelines.
- **Inputs archived:** the pre-release `globe-source-<date>` (`SOURCE_RELEASE_TAG` in `globe_data.env`, never latest) holds the eight ETOPO bands as NOAA's OPeNDAP server answered them (`etopo-band-<n>.dods`, pinned by `ETOPO_BANDS_SHA256`), the star map, the Black Marble picture, the Blue Marble Next Generation picture and the cloud picture. The script takes them from there first, each checked by SHA-256, and asks NOAA, SVS and NASA only when the archive can't be reached (`--upstream` skips it); `python3 -I Scripts/build_globe_data.py --check` on an empty `build/globe-cache/` reproduces every pin (the satellite picture takes the longest: 128 full-size tiles through the pure-Python encoder).
- To make new files: change the sources or the date in `globe_data.env` (empty pins print the new SHA-256, `ETOPO_BANDS_SHA256` empty reads NOAA), run `python3 -I Scripts/build_globe_data.py --upstream --extract <dir>` (about 150 MB from NOAA in pieces, kept in `build/globe-cache/`; prints `ETOPO_BANDS_SHA256` and copies the inputs into `<dir>`), publish `<dir>/*` as `gh release create globe-source-<date> --prerelease --latest=false`, set `SOURCE_RELEASE_TAG`, run the script, pin the printed SHA-256, publish with `gh release create globe-<date> --repo JohannesHoppe/schnellbild --prerelease --latest=false build/globe/*`. The same inputs give the same bytes (our own JPEG encoder; zlib's deflate at level 9 for the PNG; `--check`), checked on CI on macOS 15 and 26 by `globe-data-check.yml` (on every push that changes the script, its pins or the workflow, and by hand).

## VLCKit (the heavy dependency — read carefully)

AVI/MKV/WebM and other non-native formats play **in-app via vendored VLCKit
(LibVLC), as a fallback only**; native formats stay on AVKit.
AVKit stays for the native formats: both decode through VideoToolbox, but AVKit hands its pictures to the display without the copy our VLC path makes per picture (`VLCFrameOutput`), and it shows HDR (HDR10, HLG, Dolby Vision) through its `AVPlayerLayer`; `VLCFrameOutput` shows HDR10 and HLG (see Auto enhance and adjustments).

- It's **built by us from VideoLAN's source** without the GPL modules (see
  "VLCKit without GPL modules"), published as a pre-release of this repository
  and fetched + **SHA-256-verified** by `Scripts/fetch_vlckit.sh` (the zip, then the unpacked framework's tree SHA-256; a vendored copy is used only while its tree SHA-256 matches; `tree_sha256` in `fetch_verified.sh`, `fetch_unrar.sh` does the same for `Vendor/unrar`).
- Vendored to **`Vendor/VLCKit.xcframework`** (gitignored; arm64 only). `Package.swift` references it as a **local `binaryTarget`**
  (`path: "Vendor/VLCKit.xcframework"`), the executable depends on `"VLCKit"`,
  code does `import VLCKit`.
- **Deliberately NOT a third-party SPM repo.** The user is security-conscious;
  we audited the community wrapper, then chose: VideoLAN's source and build
  script + our own hash + local vendoring → minimal attack vector, no external
  repo in the trust path.
- The Mac App Store version is the same app (see "One app, two ways out"): the LGPL allows it with the custom EULA (changing and reverse engineering the library allowed) and the source offer in THIRD-PARTY-NOTICES.

## Working conventions

- **Texts people read** (website, App Store, EULA, app UI): no em or en dashes as punctuation (commas, colons, parentheses or a new sentence instead) and no gradients in anything designed: the owner reads both as signs of AI-made work. The same goes for the phrases in `~/Work/haushoppe-headquarter/haushoppe-its.de/docs/ki-floskeln.md` (buzzwords, contrast figures, intensifiers, triads) and above all for calling our own texts "honest", "fair" or "transparent" (in any language): that implies other texts of ours aren't; state the facts and leave the label out. **Every text people read goes through the project skill `lektorat` (`.claude/skills/lektorat/SKILL.md`) before it is committed**: the rules, the phrase lists in German and English, the "honest" word field in all 20 languages, and what stays allowed.
- **SEO and ASO per market:** the website's `seoTitle`, `seoDescription`, `keywords`, headings and the App Store's subtitle and `keywords.txt` are tuned per language and country to what people there search for (Google Keyword Planner data, fetched by the Google Ads session through `generateKeywordIdeas`). So the languages deliberately differ a little from the English master: a market's own search words (its word for image viewer, "MKV abspielen", the Windows viewer people look for on the Mac) go where they count; the meaning stays the same. When a text changes, keep each language's search words in it; think of SEO with every text. App Store keywords: 100 characters, commas without spaces, no words already in the name or subtitle, no other apps' names (those may appear on the website as "alternative to …"); a Store also indexes the keywords of a second locale (Germany also English (UK), the US also Spanish (Mexico)), so those don't need repeating.
- **Positioning next to IINA and Phiewer** (website lead and comparison, README intro and comparisons): Schnellbild is one free app for the pictures and videos in your folders. IINA is a full player for watching videos, Phiewer a fast photo viewer with a paid PRO version; the texts name what each does well and say who Schnellbild is for (photos and videos in one grid, a folder, a search or an archive played as the slideshow, every feature free). ## Media Extensions (native thumbnails) — what is known

Goal: teach macOS the formats it can't read (AVI, MKV …) with a MediaExtension format reader (and later a video decoder), so Quick Look, Finder and Schnellbild's own grid get system-cached thumbnails. The experiments live in `Spike/MediaExtension/` and the manual workflow `spike-media-extension.yml` (CI ignores `Spike/**`). Its downloads (the QuickLook Video DMG, the Canon AVCHD sample) are the one exception to keeping every input in this repository or its releases: the spike is not part of the app, and those files are other people's to distribute. What QuickLook Video teaches (architecture, FFmpeg build, pitfalls, links): `docs/quicklook-video-research.md`.

Seen on CI (macOS 15 and 26 runners):
- macOS lists and matches the reader when ad hoc signed, but starts it only with the entitlement `com.apple.developer.mediaextension.formatreader`, and that needs Developer ID plus the provisioning profile (App IDs `art.haushoppe.schnellbild.formatreader` / `.videodecoder`, profiles as secrets `MACOS_PROFILE_FORMATREADER` / `MACOS_PROFILE_VIDEODECODER` in the `release` environment; the profiles carry the Developer ID certificate that expires 2027-02-01 and must be generated again with a new one). Ad hoc with the entitlement: AMFI refuses it; without it: it starts, but is never asked.
- It is off until turned on in System Settings → General → Login Items & Extensions → Media Extensions; CI turns it on through the accessibility API (`ax-enable.swift`); `pluginkit -e use` doesn't.
- An app that calls `MTRegisterProfessionalVideoWorkflowFormatReaders()` gets it from AVFoundation.
- Quick Look thumbnails (`QLThumbnailGenerator`) use Media Extensions only when the asking process has opted in (`MTRegisterProfessionalVideoWorkflowFormatReaders()` and `VTRegisterProfessionalVideoWorkflowVideoDecoders()`, `Spike/MediaExtension/probe-me.swift`), and only on macOS 26: there QuickLook Video's extensions gave real MKV and WebM thumbnails and Quick Look asked our signed reader; on macOS 15 neither. A video-only AVI got none (AVFoundation reads that container itself; its codec needs a decoder).
- AVCHD (`.mts`, `.m2ts`, H.264 in 192-byte transport stream packets): AVFoundation opens it itself (opted in or not; 1.88 s for the fixture, where our reader says 2.00 s), but Quick Look's thumbnails of it on macOS 26 come only through our reader: with it on, a picture (the fixture 0.05 s; a real Canon HG10 1080/50i clip from samples.ffmpeg.org, 512×288 in 0.33 s, fields and 16:9 right); with the type claimed and the file refused by the reader, with it off, or for a process that doesn't opt in, none. On macOS 15 none either way. On the dev Mac (macOS 27, no reader installed) none, opted in or not. An x264-made interlaced test clip decodes with wrong colours in places through VideoToolbox, through our reader and through AVFoundation from an MP4 remux alike; the real camcorder clip doesn't.
- Schnellbild's own reader works: `Spike/MediaExtension/MKVParser.swift` (Matroska in plain Swift: tracks, codec setup, where each frame lies, bounds-checked) and `Reader.swift` (the MediaExtension classes; frames located with `sampleLocation`, decoded by macOS) gave AVFoundation frames on macOS 15 and 26, and a Quick Look thumbnail of an H.264 MKV on macOS 26 (0.8 s first, then from the cache), Developer ID signed with the profile, turned on, the asking process opted in. Open for the product: reading the file in parts instead of whole, hostile-file tests, VP9 and other codecs need a decoder.

Where the leads came from (QuickLook Video by Marginal, which moved to Media Extensions in its version 3):
- The asking app must opt in itself — `MTRegisterProfessionalVideoWorkflowFormatReaders` and `VTRegisterProfessionalVideoWorkflowVideoDecoders` — for Quick Look thumbnails to use Media Extensions (Finder does; ForkLift did from 4.7): https://github.com/Marginal/QuickLookVideo/issues/191, https://github.com/Marginal/QuickLookVideo/issues/197
- The thumbnailing process sometimes sees the extensions but doesn't use them (a macOS bug in the maintainer's words); its "Refresh" (`qlmanage -r cache`, killing `AudiovisualThumbnailExtension` and the extensions, Finder) helps: https://github.com/Marginal/QuickLookVideo/issues/172, https://github.com/Marginal/QuickLookVideo/issues/173, commit https://github.com/Marginal/QuickLookVideo/commit/107f71307f96e0b14e37edaad3f4f76231c7dcea
- Thumbnails need the video decoder too, and VideoToolbox hardware decoding (`VTIsHardwareDecodeSupported(kCMVideoCodecType_HEVC)`; virtual machines may lack it): commit https://github.com/Marginal/QuickLookVideo/commit/0835ef7
- Its exported types conform to `public.movie`, not `com.apple.mediaextension-content` (else the CoreMedia importer takes them): `formatreader/Info.plist` in that repo.
- A video-only AVI is read by AVFoundation itself, so the reader isn't asked; then only a decoder for its FourCC helps: https://github.com/Marginal/QuickLookVideo/issues/203
