# Schnellbild — project guide & session handover

Read this first. It's the durable memory between sessions. Keep it accurate —
update it when the facts change.

## What this is

A **fast, lean macOS image/video viewer** (SwiftUI, macOS 15+) — "Phiewer but
minimal". Motto: **an image & video viewer that just doesn't suck.** Speed
(also over network volumes) is one part of that, not the headline. It does
what Preview does well: read little, load in parallel, cache via the system,
never block the main thread.

## Architecture & key files

SwiftPM **executableTarget** `Schnellbild` (sources in `Schnellbild/*.swift`).
There is **no Xcode project for the app build**; `xcodegen` generates
`Schnellbild.xcodeproj` (gitignored) **only for the XCUITests**, from `project.yml`.

- **`BrowserModel.swift`** — `@MainActor ObservableObject`, the single source of
  truth. Holds `entries`/`allEntries`, `selection`, `mode` (.grid/.detail),
  `zoom`, `rotation`, search (`searchText` → `didSet` runs `applyFilter`;
  `searchFocused`, `isSearching`, `isFiltering` = non-blank query), history
  (`backStack`/`forwardStack` of `Location` = folder + query + selection +
  finished results, capped at `historyLimit`), `renameTarget`, `showInspector`,
  `showHelp`, sort, `activePlayer` (`PlaybackControl`, AVKit or VLCKit). `showInspector` (`ShortcutAction.info`: I and ⌘I in the grid, list, full view and slideshow, ⌘I also on Actions → Get Info through `menuShortcut`; Get Info in tiles' and rows' menus: `getInfo`) shows `InspectorView` beside the pane's content for `inspectedEntry` (the item on screen, else the one selected).
  **The pane's key bindings live in `handleKey(_:command:) -> Bool`** with the
  `KeyInput` enum — the unit-tested dispatch, always with Schnellbild's own keys; the window's (D, ⌃O, Tab, F5,
  F6, ⇧⌘C, ⇧⌘M) in `WindowModel.handleWindowKey`, and F9, F10, ⌃⌘F in the key monitor
  (`ContentView`). The keys the user set (`Shortcuts.swift`, see below) are resolved before them. Keys typed in the search field go through
  `handleSearchFieldKey` (fixed: they are the field's).
  - Search is **always recursive** and matches **folder and file names**: local
    matches at once, then `recursiveMatches` streams batches (`AsyncStream`)
    from a tree walk; debounced via `searchDebounce`. Each search is a
    `SearchRun` (results, the walk's task, the changes made during the walk,
    replayed on a late batch when they came after the batch began: `ChangeClock`, `SearchBatch.stamp`; what moves out of the searched folder leaves the results); streamed batches are merged into the sorted list (`EntryOrder.merged`), not sorted anew; the model shows one (`search`), the history may hold more. A change below the folder of a search on screen (the other pane copies into it) searches only the changed folders (`refresh(changed:)`, `searchArrivals`); the folder's listing is read again once the search is cleared. Names match through `NameMatcher` in the mode beside the field (`searchMode`, per pane, remembered; `SearchModePicker`): ignoring case without the language's rules (Turkish "I" would miss "img"), the case as typed, or an ICU regular expression (one that doesn't compile matches nothing, no walk; matched off the main thread, the folder's own items too (`NameMatcher.isCostly`, `matching`), giving up on a name after `regexTimeLimit` through ICU's progress callback, and on every name once the search is over: `matches(_:stop:)`). A `SearchRun` keeps its matcher; history reuses a run only for the same query and mode.
  - **`FileChange`** (`.moved` / `.removed`) is the one mechanism for changes
    the app makes on disk: `apply(_:)` runs it over every list the model holds
    (folder entries, search results, pending selection, history, the slideshow's items) and keeps
    the selection. Rename and trash only create the change. A batch is looked up by path (`FileChanges`: each entry through its own folders, not through every change), so trashing or moving thousands stays fast.
  - **Changes outside the app** (the Finder, a camera import, another Mac on a share): `relist` reads the folder shown again in place and `merge`s it (what went is applied as `FileChange.removed`, so results, history, marks and the slideshow follow; what came or changed is merged in where it sorts; selection, marks, search and scroll position stay; while searching, `searchArrivals` finds what matches). Without `force` it reads only when the folder's date differs from the one taken before the listing (`listedStamp`, one look off the main thread; no date, as on a share slow to answer, leaves it as it is). Triggers: FSEvents (`FolderWatch`, one per pane on the folder shown, `watchesFolder`, on for the app's panes through `watchFoldersByDefault`, not inside archives: changes in the folder relist it, changes below it make the tiles around them read previews and emptiness again (`forgetBelow`) and a search look there, `dropVanishedResults`; the folder itself moved or deleted opens the nearest folder still there, `followFolderGone`); the app or a window becoming active (`DiskEvents`: every pane of every open window, for what FSEvents doesn't report, such as other Macs' changes on a share); a volume unmounted (`volumesChanged`: a pane on it goes to the drives' level, one at the drives' level relists; mounting too); View → Reload (⌘R, `reload`: every tile's previews forgotten, a search searched again; inside an archive a new `load`).
  - A listing (`listing` → `FolderListing`) has the grid's entries and `otherFiles`: every other file (not hidden, not a later volume of an archive shown, packages included), listed by name under the grid (`OtherFilesList`) and counted in the status bar, so a folder with only such files never reads as empty. They aren't selectable; their rows (`OtherFileInteractions`, grid and list) have a context menu (rename: `beginRename(_: OtherFile)` → `renameFileTarget` → `RenameView(file:)`; reveal; trash) and drag like tiles; `applyHere` keeps `otherFiles` in step with every `FileChange`. A folder or archive that can't be listed sets `loadError` ("This folder / archive can't be read" with the system's reason), never "This folder is empty". Labels say exactly what is and what happens (no prose): check them when adding UI text.
  - ↑/↓ in the full view and slideshow (`verticalKey`): on a video the volume of every video in tenths (`changeVolume`, remembered, `PlaybackControl.setVolume`, shown by `VolumeDisplay` a moment); on a zoomed-in picture a fifth of the view further up / down (`panRequest`); otherwise nothing — paging is ← → / ⌘← ⌘→ only. Videos: ←/→ jump 10 % of the length (`skim`), ⇧←/⇧→ 1 % (`fineVideoJump`, `fineSkim`, staying in the video); `VideoProgressBar` under the position badge reads `activePlayer.progress` four times a second.
  - Sorting is `EntryOrder` (what it compares worked out once per entry, `Keyed`; names as the Finder compares them, `localizedStandardCompare`). By distance (`SortKey.distance`, `ShortcutAction.sortDistance`, ⌘6 unless changed; `ShortcutAction.sorts` holds one action per `SortKey`, in its order): from `distanceOrigin` (per pane, remembered as `distanceOrigin` in the preferences; set by `setDistanceOrigin` from an item's place, `sortByDistance(from:)`, which alerts through `locationMissing` when it has none, or from the sheet `DistanceOriginView`, `distanceOriginRequested`, which also opens when Distance is chosen without an origin); the places (`locations`) are read only while sorting by distance (`readLocationsIfNeeded`, from `entries`' didSet like the capture dates, so search results from subfolders too), 64 files a step through `LocationCache` (eight at a time, off the main thread), sorted again after a step at most twice a second; more than one step shows `locationProgress` in the status bar; another sort or folder stops it (`stopReadingLocations`). Items without a place go last in either direction; folders keep their group. Not inside archives (as for date taken). The list shows a Distance column and tiles a tooltip while sorting by distance (`knownDistance`, `GeoPoint.describeDistance`: km or mi by region). A list longer than `mainThreadSortLimit` (5 000) is sorted off the main thread (`ordered` in `load`, `resort`), again when the order or the lists changed meanwhile (`orderRevision`, `listRevision`); shorter ones at once. Changes on disk are followed in place (`EntryOrder.following`: what stays keeps its position, what moved is merged in where it now sorts), as are streamed results and a new folder (`merged`).
  - Paths are compared with `canonicalPath`: pure string work (standardized,
    `/private/var` → `/var`), no file system access, because it runs per entry
    on the main thread and must stay fast on network volumes.
  - `open(folder:)` records history; `navigateBack/Forward` restore folder,
    query, selection and the search (`SearchRun`: results, the walk, changes
    to replay). A search still running when the user leaves keeps running
    in the history (the newest `backgroundSearchLimit`; older ones stop and
    are searched again on return), so "Back" shows it without starting over.
    The stop button (`stopSearch`) ends a walk and keeps its results.
  - Moves and copies into folders (`move(_:into:how:)`: drops, F5, F6) are decided on the main thread (conflicts ask: Keep Both / Skip / Cancel, which stops the whole move, and "Apply to all" when more names are taken: `askKeepBoth` → `ConflictAnswer`, `planMove`) and carried out off it (`FileActions.run`, the live ones through `LiveFiles`; a test's spy inline); `transfersRunning` shows in the status bar, and `finishMove` applies the result: per item a `TransferOutcome` with the files done (a split archive's first parts also when a later one failed: their `FileChange`s and Undo) and the one that failed, reported together (`TransferFailure`). A copy (`LiveFiles.copy`, also a move to another volume, which then removes the original) is written under a hidden temporary name in the target folder (`.schnellbild-copy-<UUID>`, `isPartialCopy`) and renamed once complete, never over a name taken; on failure it is removed, and a listing removes leftovers of that exact pattern that this process isn't writing (`PartialCopies`) and that haven't changed for 12 hours (another Mac may be copying into a share). Moves on one volume are renames.
  - New folder (⇧⌘N, `beginNewFolder` → `NewFolderView` → `createFolder`): nothing is made until the name is confirmed; the folder is added to the listing and selected. Tiles drag (`TileDrag`: the file for the Finder, plus an own-process type so the window's drop zones stay away) onto a folder tile or `..`: `move(_:into:)` moves on the same volume and copies to another (`FileActions.transfer`), applies `FileChange.moved`, and drops what left the folder from its listing. Not in archives.
  - Renaming a folder or file (`rename`, also from the full view; a file must keep a media extension) never navigates: folder, query and
    results stay; the folder and everything listed inside it get the new path
    (`FileChange.moved`), as do history entries and results still streaming in.
    `FileActions.conflicts` refuses a target that is a different item (also
    the case-variant on case-sensitive volumes such as NAS shares); the live
    case-only move goes via a temporary name and rolls back on failure.
    ⌘↑ / `..` = enclosing folder (`goToParentFolder`; above "/" the drives' level `/Volumes`, nothing above that: `parentFolder`, `isDrivesLevel`; drives show an icon and are never read for previews or emptiness, `FolderTile.driveImage`, nor renamed, moved or trashed, `isDrive`, `canChange`; `com.apple.*` mounts are left out); Backspace is Back (`leaveDetailOrGoBack`: out of the full view, else `navigateBack`, with no history the enclosing folder).
  - Side effects (Finder, open, trash + confirm alert (one name: "Move “x” to the Trash?"; several: counted through `Localizable.stringsdict`, the names below), move/rename) go through
    the injectable `FileActions`; tests pass a spy. `--ui-testing` makes the app
    use its own `UserDefaults` suite (`--reset-state` clears it).
  - As in the Finder, Space opens the selected item and Return renames it (`beginRename`; on `..` both go up); in the full view Return goes back to the grid, in the search field it opens the selected result.
  - ⌘⌫ / ⌘↩ return `false` from `handleKey` so they reach their menu items
    (the local key monitor sees keys before menu key equivalents). While a
    text field is edited the monitor hands them to the field editor instead
    (`ContentView.textFieldTakes`, also ⌘ with an arrow), so they edit the
    text. Keys with ⌥ pass untouched except ⌥← / ⌥→ (turn the picture, `handleKey(option:)`); keys with ⌃ pass untouched, except ⌃⌘F (full screen, through
    `FullScreenSwitch`) and ⌃O (the dual pane). On a layout without Latin
    letters a letter key is read as on the user's Latin layout (`LatinKeys`).
  - Packages (`.photoslibrary`, `.app`) are single items, as in the Finder:
    `entry(for:keys:)` drops them, so listing, search and slideshow never
    walk into them (`containsMedia` skips them too); one dropped, opened with `--open=` or saved as the last folder opens its folder with it selected (`isPackage`). Symbolic links count by what they point to: a link to a folder is an entry at the link's own URL (trash, rename, move, marks and the tile's id act on the link, as in the Finder) with `GridEntry.linkTarget`; opening it, its previews, emptiness, bookmark, slideshow and drops go to `browseURL` (on `/Volumes`, "Macintosh HD" → `/` stays a drive). A link to a file must lead to the same media kind, one named like an archive to an archive of the same format and extension. The slideshow's walk doesn't follow links (`isLink`), nor do the enumerators, nor a search's `FolderFacts`.
  - Marking: the ⇧ range starts at `markAnchor`, a path (re-sorts and search batches move items); plain arrows, Home and End reset it. Marks that leave the listing are dropped.
  - Rename, new folder (`renameOnDisk`, `createFolder`) and Keep Both's free names (`TransferProbe.freeNames`) touch the disk off the main thread, the live actions through `LiveFiles`; the Trash prompt waits for an archive's parts to be listed (`trashLookupPending`).
  - SVG is an image like any other. ImageIO can't read it, so the full view
    draws it with `NSImage` (`VectorPicture`, in `FullImageView.swift`) at
    the view's size, larger when zoomed in; QuickLook makes its tiles. PDFs are vector pictures too (ImageIO reports no size for them), drawn by PDFKit (`PDFPages.swift`) page by page in the full view, like a video's seek: `skim` on a PDF turns its pages (`showPDFPage`; each page at fit and upright, zoomed, panned and turned on its own), before the first and after the last page `page` goes to the previous / next item (not with a key held down, as at a video's ends), so the actions `fullPrevious` / `fullNext` (← →, as in Phiewer ⌘← ⌘→, or the user's keys) turn pages and `fullPreviousItem` / `fullNextItem` leave at once; ⇧← ⇧→ (a video's fine steps) do nothing. The page on screen is `pdfPosition` (url, page, count), set by `FullImageView` once the PDF is open (`pdfOpened`; the same PDF again keeps its page), cleared by `resetTransforms`, so a PDF shown again starts at its first page; a PDF not open yet is left with ← → like a picture. Only in the full view (`pagedPDF`): the slideshow shows a PDF as one item, its first page. The badge adds "Page 3 / 12", the mini keyboard has its own row (`MiniKeyboard.Context.pdf`), tiles and the Inspector show the first page (`VectorPicture` → `PDFPages`).
  - Full screen goes through `FullScreenSwitch`: a request during the
    window's animation (an empty slideshow ending at once) is carried out
    when it ends, each window on its own (its animation, its waiting request). Window actions use `BrowserModel.appWindow` (the main
    window; the key one can be the Adjustments popover).
- **`DualPane.swift`** — `WindowModel`: each pane's `onFileChange` hands its `FileChange`s to the other pane (`adopt`: its lists, history and the folder shown follow a rename, move or trash); only the active pane's changes reach the window's views and menus. the window's one or two panes (`left`, `right`, each a `BrowserModel`; the right one keeps its own last folder and sort through `settingsPrefix`), `active` (Tab), `dual` (D, ⌃O, remembered), `split` (the left pane's share of the width, dragged on `PaneDivider` in `ContentView`, remembered; double click: half; `PaneDivider.leftWidth` lays them out, `pane(atX:width:)` finds the pane under a trackpad pinch), `sendToOtherPane` (F5 or ⇧⌘C copy / F6 or ⇧⌘M move the active pane's `actionEntries` into the other's folder; refused with `SendRefusal` while the other pane shows search results, as drops are; ⇧⌘C / ⇧⌘M because the F-keys need fn on a Mac keyboard: ⌘C / ⌘M stay Copy and Minimize, ⌥⌘M is Minimize All, ⇧⌘C / ⇧⌘M are free in the app and in macOS), `handleWindowKey` (the window's keys before the pane's). A pane's `onFoldersChanged` makes the other pane `refresh()` when it shows a changed folder; volume and mini keyboard are kept in step. Tiles dragged over a pane where they would land in its folder (`paneDropFolder`: free space and bars via `PaneDrop`, non-folder tiles via `FolderDrop`) set `dropIntoFolderTargeted`: `PaneDropHint` outlines the pane and names the folder. A move leaves out what is gone since it was dragged (`TransferProbe.gone`, lstat in the look off the main thread): on CI (macOS 26) a tile dragged into the other pane was now and then dragged and dropped a second time, its `onDrag` called again about a second after the first drop without a mouse down the app saw, and that second move asked whether to keep both copies of the file the first had moved, a modal alert that took the next keys. `NortonMenus`: F9 (the app's menus in the window), F10 (quit after asking). Marking (`BrowserModel.marked`: ⌘-click, ⇧-click, ⇧-arrows, ⌘A, Insert or M (Mac keyboards have no Insert; ⌃Space is the input source switch); Esc unmarks) feeds `actionEntries`, which trash, F5/F6 and dragging use. Norton Commander's F-keys are a second way next to the Mac keys (F3 open, F4 default app, F6 rename in a single pane / ⇧F6, F7 new folder, F8 trash); where they collide the Mac key wins (F2 renames, not Norton's user menu). Menu titles carry no key hints: keys with ⌘ or ⌃ are real `keyboardShortcut`s (as set, `Shortcuts.menuShortcut`), letters and F-keys are taught by F1 and the mini keyboard. Keys are shown as on Apple's keyboards (⌫ ↩ ⎋ ⇥ ↖ ↘, the space bar by its name in the user's language: `KeyChord.text`; `ShortcutsTests.testKeysAreShownAsOnApplesKeyboards`, `LocalizationTests.testKeyNamesAreGlyphsOrTranslated`); no word appears twice in a mini keyboard row in any language (`testNoDuplicateWordsWithinAMiniKeyboardRow`).
- **Windows (⌘N)** — `WindowGroup(id: "browser")` → `WindowRoot`, one `WindowModel` per window (`WindowModel.claim`: the first window's model, made at launch, for a window while no other shows it; else a new one numbered by the lowest free number, its settings under `window<n>.` and `window<n>.rightPane.`, opening on its own last folder or the folder of the window it was opened from). `WindowAttach` ties the model to its `NSWindow` (`nsWindow`) and calls `windowClosed` (slideshow, full view, search end; the model is `closed`: no other pane's changes reach it and its observers stop (`leaveWindow`), until `claim` takes it again and `reopen` reads its folders afresh). `WindowModel.of(_:)` / `current` (key window, else main): the one key monitor sends each key to the window it was typed in, `ModifierClicks` keeps each window's tile frames apart, full screen and slideshows use the pane's `hostWindow`; the menus and Settings follow `WindowFocus.current`. `FileChange`s and changed folders go to every pane of every window. Bookmarks, caches and the slideshow time are app-wide.
- **`ContentView.swift`** — `ContentView` → `WindowView` (toolbar, key monitor, drop zones, mini keyboard, slideshow full screen; works on `window.active`) showing one `PaneView` or two side by side (`pane.left` / `pane.right`, the active one outlined); a `PaneView` is one pane's grid / full view, search bar, status bar and sheets.
- **`SearchField.swift`** — `NSSearchField` wrapper, always visible above the
  content. It refuses first responder until clicked or ⌘F, otherwise AppKit
  focuses it on launch and it swallows the grid keys.
- **`Bookmarks.swift`** — folder bookmarks (`Bookmarks.shared`, both panes, paths in the preferences, `makeDefaults()` so UI tests keep theirs): ⌘D toggles the folder shown, ⌃1 … ⌃9 open the first nine (`BookmarkItems`: the Bookmarks menu, the toolbar's star `BookmarksButton`), a folder tile's context menu adds / removes; `apply` hands every `FileChange` to `follow`, so a rename or move by the app carries the bookmark along.
- **`FolderWatch.swift`** — `FolderWatch` (an FSEventStream on one folder and below, on a queue of its own, latency 0.5 s, the app's own changes left out (`IgnoreSelf`: they arrive as `FileChange`s), the watched folder itself through `WatchRoot`; more than `namedLimit` folders at once, or events the system dropped, come as nil: read it all again) and `DiskEvents` (unmount / mount, app and window activation). FSEvents reports only changes made on this Mac, also on network shares: the activation relist covers the rest.
- **`Undo.swift`** — `FileHistory` (one per window, both panes; `BrowserModel.undoHistory`): every rename (also the folder shown, from the title bar), trash (`LiveFiles.trash` returns where the item lies in the Trash), move and copy (`finishMove`) is recorded as an `UndoStep` of parts, each with the `ItemIdentity` of the item where it lies (volume + file number by `lstat`; a copied folder also a hash of its relative paths); `undo()` / `redo()` carry them out off the main thread (`onFiles`), one at a time (`running`; the menu items are disabled meanwhile), only on that very item (another file that took the name, a copied folder something was put into since: refused, `UndoError`) and never over a name taken meanwhile. A failure asks (`FileActions.keepFailedUndo`): keep what wasn't done on top to try again, or forget it so Undo reaches the older steps. Taking an item out of the Trash may be denied in the App Sandbox: then it says to use the Finder's "Put Back". The `FileChange`s are applied (the folder shown follows its own rename undone, `followFolder`) and the folders that got something back are read. Only in the context menus (`UndoMenuItems` on top of tiles', rows', other files' and the free space's), no keys on purpose.
- **`BossKey.swift`** — X (not while typing) makes every window invisible and click-through (alpha 0, kept open so the app's keys still arrive), hides the app and mutes the players (`BrowserModel.audibleVolume`, `BossKey.changed`); while engaged the key monitor hands every key to `BossKey.typed`: ⌘Q quits, X X X (`Counter`, each within a second) restores (`release`), as does a click on the Dock icon (`applicationShouldHandleReopen`). A window in full screen leaves it first (its space would stay black behind the invisible window); the app hides once it has (`hideAfterFullScreen`), and X X X puts it back into full screen (unhiding the app). `testBossKeyInFullScreen` checks only the leaving and hiding: XCUITest's keys to the hidden app brought it back in some CI runs and not in others (macOS 15 and 26; why is not known).
- **`Shortcuts.swift`** — the user's own keys. `ShortcutAction` is every action that has keys (about 90, grouped as F1 shows them, `ShortcutGroup`); each one's `Spec`: where its keys work (`ShortcutScope`: grid, full view, slideshow, the playlist while it has the keys), Schnellbild's keys (`standardKeys`), Phiewer's where they differ (`phiewer`, only for actions Schnellbild has: ← → the item, ⌘← ⌘→ skim, ⌫ trash, ⌘R rename, ⌥⌘L grid / list, ⌥⌘S slideshow; nothing invented for Phiewer's other features), and how it is carried out (`performer`: a key handed to `handleWindowKey` / `handleKey`, or `.command` for what a menu item, F9, F10 or the boss key does, `WindowModel.performCommand` under the menu item's conditions). `KeyChord`: a key with its modifiers (letters lower case with ⇧ apart, other characters carry ⇧ in themselves, "=" is "+"), its stored form ("@$c" = ⇧⌘C, Cocoa's ^ ~ $ @), `text` as Apple shows keys, `menuShortcut` (only with ⌘ or ⌃: letters and F-keys stay out of the menus), `from(event)`. `Shortcuts.shared` (app-wide, `BrowserModel.makeDefaults()`): the preset (`ShortcutPreset`: `schnellbild`, `phiewer`) and per action the keys that differ from it, in the preferences `keyboardShortcutsPreset` / `keyboardShortcuts` (unknown actions, unreadable and reserved keys dropped; a key two actions claim where both work stays with the changed one). `assign` takes the key from every action whose scope overlaps (`conflicts`); `reset`, `resetAll`, `choose` (a preset replaces own changes); `isReserved` (⌘Q ⌘W ⌘H ⌘M ⌘, ⌘` ⌃⌘F ⌘C ⌘V ⌘X ⌘Z …). **Typed keys:** the key monitor first asks `WindowModel.handleTyped` → `Shortcuts.resolve` in the window's `shortcutContext`: `.standard` (one of the action's own Schnellbild keys) and `.free` (no action's key) go on to the key bindings exactly as before; `.custom(action)` (a key the user or a preset gave it) is carried out by `WindowModel.perform` (the performer key with `playlistKeysOff`, so a slideshow key that is one of the playlist's own reaches the slideshow); `.blocked` (Schnellbild's key of an action here that now has others) does nothing. While typing in a field only keys with ⌘ / ⌃ and F-keys are resolved (not ⌘A ⌘C ⌘V ⌘X ⌘Z). `WindowModel.typeKey` is the monitor's path without its own keys, for tests. The boss key's release (three times) and `WindowOpener` (New Window's key) follow too. Where keys are shown, they come from here: F1 and its print (`ShortcutsHelpView.groups(_:)`, rows of `HelpKeys`: an action's keys, a pair, a range "⌘1 … ⌘5", fixed keys (⌘Q, ⌃⌘F, the search field's), words), the mini keyboard (`MiniKeyboard.Key`: the action and Schnellbild's key, which a click sends and which is its UI-test id; the cap is that key while the action has it, else its first; none: left out), menu items (`.keyboardShortcut(shortcuts.menuShortcut(…))`), tooltips (`hint`, "no key"), `ShortcutLabel` and `KeyCap` (`capText`: Esc as "esc").
- **`ShortcutsSettingsView.swift`** — Settings → Keyboard: the preset (segmented), Reset All, a search field (`Shortcuts.matches`: the action's name, or its keys as glyphs or by name, "cmd shift r", through `keySearch`), the actions in `ShortcutGroup` sections (Changed / Phiewer badges, "only actions whose keys differ from Schnellbild's"), each with its keys as caps (click: record a key in its place, `+`: one more, right-click or the trash while recording: remove, ↺: the preset's keys). Recording is a local key monitor that takes the next key (Esc and ⌫ too; Cancel button). A reserved or unusable key says so under the row; one another action holds asks ("Reassign"). Changing the preset with own changes asks first.
- **`SettingsView.swift`** — Settings (⌘,, SwiftUI's `Settings` scene, tabs General and Keyboard): General (`GeneralSettingsView`) holds the slideshow's picture time (`WindowModel.slideshowSeconds`, 1–60 s, `BrowserModel.slideshowSecondsKey`, both panes) and forgetting the saved archive passwords (`ArchiveStore.forgetPasswords`: the keychain list and the archives a password opened).
- **`RenameView.swift`** — the F2 rename sheet (`model.rename`); for files the base name is preselected. While it is open, `applyHere` carries `renameTarget` / `renameFileTarget` through every `FileChange` (the other pane renamed it: the sheet shows the new name) and closes it when the item is gone.
- **`ContentView.swift`** — one **local `NSEvent` keyDown monitor** maps key
  codes and hands each key, via `MainActor.assumeIsolated`, first to
  `WindowModel.handleWindowKey` (D, ⌃O, Tab, F5, F6, ⇧⌘C, ⇧⌘M), then to the active
  pane's `model.handleKey`; F9 / F10 (`NortonMenus`) it runs itself, outside
  text fields, sheets and slideshows. Keys are deliberately focus-independent,
  because SwiftUI focus can swallow Backspace/arrows. F1 works everywhere

## Security: files from others

Viewing must never run anything. What is in place:
- Archives are only read, never extracted to disk; entry names are cleaned (`..`, `.`, empty parts dropped). Reads into memory are capped at 256 MB (`ArchiveStore.largestRead`), also for whole files read from disk (`MediaData.read`: SVG, PDF). An archive's index holds at most 1 000 000 entries, the folders their paths imply included (`ArchiveStore.indexLimit`): a header flood can't fill memory; the rest is left out and the archive counts as read in part (`complete` false). `CraftedArchiveTests.testAnIndexStopsAtItsLimit`.
- VLC (`VLCSafety`): every media, the thumbnailer's too, gets one demuxer: the video container its first 512 bytes show (`VLCSafety.container`: Matroska, transport stream at 188 or 192 bytes, MP4, AVI, MPEG-PS, ASF, FLV, Ogg; a recording named `.mkv` that is a transport stream plays), else the one its extension names, and only for a file with a video extension (`VLCSafety.reader`: `.wmv` → `asf,none`, `.flv` → FFmpeg held to its `flv` format, unknown → `none`), so a "video" that is really an HLS playlist can't make VLC fetch from the network. One demuxer, never a list: VLC treats a demuxer it is told to use as forced, and `ps` / `ts` then take any file, so everything after them in a list would get nothing. `VideoFormatTests` gets a frame from a clip of every listed extension and checks a playlist named like a video, whose segment is a clip on disk, gives none; no subtitle files picked up. Media also get `:no-mkv-preload-local-dir` (else the Matroska reader opens the folder's other .mkv / .mka / .mks files looking for linked segments) and `:no-mkv-use-chapter-codec` (chapter codecs are DVD-style menu programs inside the file). VLCKit reads its libVLC options from the preference `VLCParams` through `UserDefaults.standard`, which also searches the global domain any local program can write; at launch (app and thumbnail extension) `VLCSafety.forgetInjectedOptions` sets the app's own domain to VLCKit's own default list (`VLCSafety.libraryOptions`, copied from `-[VLCLibrary _defaultOptions]` of VLCKit 3.7.5: check it when updating VLCKit) and drops a `-VLCParams` launch argument. Lua is not in the bundled VLCKit and its modules are static.
- AVFoundation: every `AVURLAsset` of a file someone else made (`VideoDetailView`, `ArchiveResourceLoader`) has `AVURLAssetReferenceRestrictionsKey` = `forbidAll`: a reference movie can't make it read other files or the network.
- The media extension's parsers (`MatroskaIndex`, `TransportIndex`) hold times within `MatroskaIndex.largestTime` (Matroska) or the 33-bit clock (transport streams), and the format reader adds and subtracts them saturating (`saturatingAdd` / `saturatingSubtract`), so a crafted duration, time scale or timestamp can't trap; `ContainerTests.testTimesOutOfRangeAreHeldInRange`. File names are logged `.private`.
- Open with Default App (`LiveFiles.openWithDefaultApp`, `openableTarget`): links and aliases are resolved and must lead to a file of their own extension, and only pictures, videos, PDFs, folders and archives of the grid's formats (`ArchiveName.format`) are opened, each with the app for its type; never apps, packages, scripts, installer packages, disk images, xip or Apple archives (they conform to `public.archive` too, and opening them installs or mounts), nor web content (`refusedTypes`). Finder aliases are listed among the other files; a symbolic link counts by what it points to, and a linked folder is listed as the link (trash, rename, move act on it) and opens its folder.
- Other files (`LiveFiles.openOtherFile`, double click / Open in their menu): only documents that hold no program (an allow list of types: text, PDF, office, audio …; a refuse list of types and extensions: executables, apps, packages, scripts, installers, disk images, Terminal settings, Finder locations, and active web content a browser would run: HTML, XHTML, XML, web archives, SVG …; links and aliases resolved first), a .webloc / .url only to an http(s) address, opened with `NSWorkspace.open`. `OpenOtherFileTests`.
- A folder reopened at launch is remembered until the app has run 15 s or quits normally (`restoreUnconfirmed`, per pane of every window; a normal quit clears them all): if the app ended before, the next launch doesn't reopen it (`skippedRestore`), so a file that crashes the app can't crash every launch.
- The app and its extensions run in the App Sandbox (see "One app, two ways out"): no network, no other programs started, only the folders the user opened to it; the release app has the Hardened Runtime (library validation); the thumbnail extension reads only the file QuickLook hands it, also when Finder asks for an MKV's thumbnail; no document types or URL schemes; `--open=` and the UI-test switches are command-line only.
- Media Extensions (opted in at launch) run each in its own sandboxed process, and only those the user turned on in System Settings.
- The app itself never goes online: no MapKit, no geocoder. The Mac's position is asked for only when the user clicks Use My Location (macOS asks first; one request) and stays in the app as the distance origin; the privacy policy says so (`site/i18n`, `privacy.stays`). The Inspector's Open in Maps hands an `https://maps.apple.com/?ll=…` address to `NSWorkspace.open` (Apple Maps goes online, the UI says so); coordinates and map links pasted are parsed offline (a short link can't be, and the sheet says why).
- Metadata beside and inside files (`MP4Boxes`, `GPMF`, `XMPMetadata`, `SonyClipXML`, `DJIFlightLog`, `GPXTrack`) is parsed by our own code that checks every size, offset and count and caps what it reads (index 64 MB, XMP 16 MB, clip XML 4 MB, GPX 64 MB, flight logs 128 MB, samples 4 MB); the XML readers refuse a document type (entities) before XMLParser sees it. Read only, never written. `MetadataSourceTests` feeds them damaged and crafted input.
- The offline map reads only its own files from the app bundle (SHA-256-checked at build time); its readers (`PMTilesArchive`, `VectorTile`, `PlaceIndex`, `Gzip`) still check every offset and length, so a damaged file reads as missing tiles or places (`OfflineMapTests.testBrokenTilesThrowOrReadLessNeverCrash`). The app never goes online for the map; the credit's link opens openstreetmap.org/copyright in the browser. The globe reads only its own files from `Resources/Globe` (SHA-256-checked at build time); `Heightmap` checks the header and the length, the pictures go through ImageIO.
- PDFs (`PDFPages`): read into memory like any picture (`MediaData.read`, the 256 MB cap, also inside archives), opened with PDFKit's `PDFDocument(data:)` (a locked one isn't shown) and only drawn into bitmaps with `PDFPage.draw(with:to:)`; no `PDFView`, so nothing is clicked or carried out: PDFKit's headers name `PDFAction` (go-to, named, remote go-to, reset form, URL) as what a user triggers through a `PDFView` (`performAction`, its delegate's link clicks), and none for JavaScript. Annotations are drawn as they look.
- Remaining risk: the parsers run in the app's process (VLC with FFmpeg, UnRAR, the system's libarchive, ImageIO, PDFKit for PDF, AppKit for SVG), several already while a folder is browsed (thumbnails, archive indexes). A bug in one of them could run code with the app's rights, which the sandbox limits to the folders opened to it, without network. A further step would be a sandboxed XPC helper (read-only, one file) for VLC and the archive readers; VLC's frames are IOSurfaces already, which can cross XPC. Until then: keep VLCKit and UnRAR current with their security releases.

## Globe data

The globe's data is made by `Scripts/build_globe_data.py` (standard library, `python3 -I`, plus `swift Scripts/convert_globe_images.swift` for the two pictures through ImageIO) from the sources in `Scripts/globe_data.env` and published as assets of the pre-release `globe-<date>` of this repository (never latest); `Scripts/fetch_globe.sh` (called by `fetch_vlckit.sh`, so by every build and CI, which caches it with `Vendor/`) downloads them into `Vendor/Globe` (gitignored), each checked against its SHA-256; `build_app.sh` and `project.yml` copy them into `Contents/Resources/Globe`. The notice is `Resources/Licenses/Globe-data.txt` (committed); credits in the About window, THIRD-PARTY-NOTICES.md and the README.
- **Elevation:** NOAA ETOPO 2022, its 30 arc-second surface elevation grid (CC0 1.0; "not to be used for navigation"; cite https://doi.org/10.25921/fd45-gt74), every fifth sample read through NOAA's OPeNDAP server in eight bands, 3 × 3 of them averaged into cells of 1/8° (each block centred on its cell), whole metres: `schnellbild-heightmap-<date>.sbhm`, 2880 × 1440 int16 (8.3 MB, the format in `GlobeData.swift`). Averaging lowers the summits (Everest's cell about 5 900 m).
- **Night sky:** NASA SVS "Deep Star Maps 2020" (svs.gsfc.nasa.gov/4851; SVS content is public domain; from Gaia DR2, Hipparcos and Tycho-2), the 4k star map (EXR, pinned by size and SHA-256), tone-mapped to an 8-bit sRGB JPEG of 4096 × 2048 (`schnellbild-sky-<date>.jpg`, 4 MB): right ascension 0h in the middle, increasing to the left, declination +90° at the top. The Yale Bright Star Catalogue is not used (HEASARC provides it for research only; Yale keeps the copyright), nor Hipparcos / Tycho / Gaia directly (CC BY-NC).
- **City lights:** NASA Earth Observatory's Black Marble 2016, grey, 3 km (13500 × 6750, pinned by SHA-256), resized to 5400 × 2700 (`schnellbild-citylights-<date>.jpg`, under NASA's media usage guidelines).
- To make new files: change the sources or the date in `globe_data.env` (empty pins print the new SHA-256), run the script (about 150 MB from NOAA in pieces, kept in `build/globe-cache/`), pin the printed SHA-256, publish with `gh release create globe-<date> --repo JohannesHoppe/schnellbild --prerelease --latest=false build/globe/*`. The heightmap is the same bytes for the same data (`--check` compares it); the JPEGs are ImageIO's and may differ between macOS versions.

## VLCKit without GPL modules

VLCKit as VideoLAN builds it carries 8 VLC modules that state the GPL (Dolby Surround decoder, mono downmix, the dummy interface, syslog, the RTSP VoD server, stream output cycle and RTP, the rotate filter); `Scripts/vlckit_licenses.py <binary>` lists them (names from `nm`: the linker folds the identical licence functions into one, so the disassembly alone names one module for many). The App Store's terms don't go with the GPL. `Scripts/build_vlckit_lgpl.sh` (workflow `vlckit-lgpl.yml`, by hand, about an hour: VLC's libraries build one at a time, `MAKE_JOBS=1`, since its ninja and macOS's make 3.81 don't share jobs) builds VLCKit 3.7.5 (VLC 3.0.24) with VideoLAN's own `buildMobileVLCKit.sh` (macOS, arm64), a `sha512sum` that reads check lines from standard input (VLC's downloads), with the current Xcode. Added to `buildMobileVLCKit.sh`'s list of modules to delete (it deletes every plugin library whose file name contains an entry, so each entry is a whole `lib<name>_plugin` name from VLC's `modules/*/Makefile.am`): the 8 GPL ones (`GPL_MODULES`) and those a viewer of local files never needs (`UNNEEDED_MODULES`; with them 44 of the 236 modules VideoLAN's build makes for macOS go, a few entries name modules it doesn't make): every network access (HTTP old and new, FTP, SFTP, SMB via libsmb2 and libdsm, NFS, live555's RTSP, UDP, TCP, RIST, SAT>IP, MMS, RTP, SDP, FFmpeg's avio, SRT), concat, VDR (priority 60 for every `file://`: in a VDR recording's folder it opens the other files), every access output, the standard stream output, Chromecast, service discovery (Bonjour, UPnP, mDNS), playlists, adaptive streaming, the directory and NSC demuxers, the stream filters decomp (starts `zcat` / `bzcat` / `xzcat` on compressed content, also while the thumbnailer reads a folder), HDS and record, VLC's libarchive stream extractor, the keystores (file, keychain, memory), SecureTransport TLS, the folder art finder, Lua, Flaschen-Taschen (UDP video output), the audio file output, the demux dumper. Kept: the access modules `filesystem` (`file://`), `imem` (`imem://`, what `libvlc_media_new_callbacks` and so `VLCMedia(stream:)` open), `attachment`, `idummy`, `timecode`; all demuxers, decoders, packetizers, filters and outputs of local playback. Names in the binary (`vlc_entry__<name>`) are the source's path in `modules/` (VLCKit's patch 0009, `MODULE_FULLNAME`), e.g. `access_http_access` is `libhttps_plugin`. It fails unless every module states the LGPL and none of the left-out ones is in it (`vlckit_licenses.py --no-gpl --local-only`; 192 modules); then the unit tests run against it (`SCHNELLBILD_OWN_VLCKIT=1`) and it is published as a pre-release of this repository (`vlckit-3.7.5-lgpl-<run>`, never latest) together with `VLCKit-third-party-licenses.txt` (the licence files at the top of every library VLC's contrib build unpacked and built, a folder with a `.<name>` stamp in the build folder, FFmpeg's among them, and the list of static libraries linked) and the complete source (`VLCKit-3.7.5-source.tar.gz` and `VLCKit-3.7.5-build-changes.patch`, VLC with VLCKit's patches applied, `VLCKit-contrib-sources.tar`: the libraries' downloads); the notes give the zip's SHA-256 and the unpacked framework's tree SHA-256. `Scripts/fetch_vlckit.sh` fetches it by both for every build (`SHA256`, `TREE_SHA256`).
VLC's third-party libraries (`contrib`) are linked into VLCKit whether or not a module uses them: the build links every static library in the contrib prefix. The current build carries its own libarchive 3.8.9 (exported `archive_read_*`, hence `libarchive_shim.cpp`'s `dlsym`).

## VLCKit (the heavy dependency — read carefully)

AVI/MKV/WebM and other non-native formats play **in-app via vendored VLCKit
(LibVLC), as a fallback only**; native formats stay on AVKit.
AVKit stays for the native formats: both decode through VideoToolbox, but AVKit hands its pictures to the display without the copy our VLC path makes per picture (`VLCFrameOutput`), and it shows HDR (HDR10, HLG, Dolby Vision) through its `AVPlayerLayer`; `VLCFrameOutput` shows HDR10 and HLG (see Auto enhance and adjustments).

- It's **built by us from VideoLAN's source** without the GPL modules (see
  "VLCKit without GPL modules"), published as a pre-release of this repository
  and fetched + **SHA-256-verified** by `Scripts/fetch_vlckit.sh` (the zip, then the unpacked framework's tree SHA-256; a vendored copy is used only while its tree SHA-256 matches; `tree_sha256` in `fetch_verified.sh`, `fetch_unrar.sh` does the same for `Vendor/unrar`).
- Vendored to **`Vendor/VLCKit.xcframework`** (gitignored; arm64 only). `Package.swift` references it as a **local `binaryTarget`**
  (`path: "Vendor/VLCKit.xcframework"`), the executable depends on `"VLCKit"`,
  code does `import VLCKit`.
- **Deliberately NOT a third-party SPM repo.** The user is security-conscious;
  we audited the community wrapper, then chose: VideoLAN's source and build
  script + our own hash + local vendoring → minimal attack vector, no external
  repo in the trust path.
- The Mac App Store version is the same app (see "One app, two ways out"): the LGPL allows it with the custom EULA (changing and reverse engineering the library allowed) and the source offer in THIRD-PARTY-NOTICES.

## Working conventions

- **Texts people read** (website, App Store, EULA, app UI): no em or en dashes as punctuation (commas, colons, parentheses or a new sentence instead) and no gradients in anything designed: the owner reads both as signs of AI-made work. The same goes for the phrases in `~/Work/haushoppe-headquarter/haushoppe-its.de/docs/ki-floskeln.md` (buzzwords, contrast figures, intensifiers, triads) and above all for calling our own texts "honest", "fair" or "transparent" (in any language): that implies other texts of ours aren't; state the facts and leave the label out. **Every text people read goes through the project skill `lektorat` (`.claude/skills/lektorat/SKILL.md`) before it is committed**: the rules, the phrase lists in German and English, the "honest" word field in all 20 languages, and what stays allowed.
- **SEO and ASO per market:** the website's `seoTitle`, `seoDescription`, `keywords`, headings and the App Store's subtitle and `keywords.txt` are tuned per language and country to what people there search for (Google Keyword Planner data, fetched by the Google Ads session through `generateKeywordIdeas`). So the languages deliberately differ a little from the English master: a market's own search words (its word for image viewer, "MKV abspielen", the Windows viewer people look for on the Mac) go where they count; the meaning stays the same. When a text changes, keep each language's search words in it; think of SEO with every text. App Store keywords: 100 characters, commas without spaces, no words already in the name or subtitle, no other apps' names (those may appear on the website as "alternative to …"); a Store also indexes the keywords of a second locale (Germany also English (UK), the US also Spanish (Mexico)), so those don't need repeating.
- **Positioning next to IINA and Phiewer** (website lead and comparison, README intro and comparisons): Schnellbild is one free app for the pictures and videos in your folders. IINA is a full player for watching videos, Phiewer a fast photo viewer with a paid PRO version; the texts name what each does well and say who Schnellbild is for (photos and videos in one grid, a folder, a search or an archive played as the slideshow, every feature free). Claims about the other apps come from their own sites (iina.io, IINA's README and default key bindings; phiewer.com with its lite / PRO table, its App Store pages) and carry an "as of" month.
- **Work directly on `main`, no feature branches.** There is a single developer. **Commit locally while working on a set of features and push once when they're all done**, so CI doesn't run (and cancel itself) on every small commit. Typecheck locally as far as possible before that push (see Build / test / run).
- **Verify heavy / UI changes on CI, not locally.** Local runs of the app,
  XCUITests, code-signing, or `sudo` pop macOS dialogs (Gatekeeper, Touch ID,
  license) that interrupt the user.
  - Fine locally (no popups): `./Scripts/typecheck.sh` (works with only the Command Line Tools: app, unit and UI tests are typechecked, with stand-ins for SwiftUI's `@State` macro and for XCTest in `Scripts/typecheck/`; run it before every commit), and with a full Xcode `./Scripts/test.sh`, `swift build`.
  - Prefer CI (push → watch): running the `.app`, XCUITest, `build_app.sh`,
    anything that signs or launches a freshly-built bundle.
  - Only fall back to local launches when CI genuinely can't answer — say so first.
  - **Keep the README current.** Whenever a feature, key binding or anything else users see changes, check README.md (features, keyboard tables, screenshots) and the F1 help (`ShortcutsHelpView.swift`) and update them in the same commit. Build/test instructions live in `BUILDING.md`; the README sells the product.

## Media Extensions (native thumbnails) — what is known

Goal: teach macOS the formats it can't read (AVI, MKV …) with a MediaExtension format reader (and later a video decoder), so Quick Look, Finder and Schnellbild's own grid get system-cached thumbnails. The experiments live in `Spike/MediaExtension/` and the manual workflow `spike-media-extension.yml` (CI ignores `Spike/**`). What QuickLook Video teaches (architecture, FFmpeg build, pitfalls, links): `docs/quicklook-video-research.md`.

Seen on CI (macOS 15 and 26 runners):
- macOS lists and matches the reader when ad hoc signed, but starts it only with the entitlement `com.apple.developer.mediaextension.formatreader`, and that needs Developer ID plus the provisioning profile (App IDs `art.haushoppe.schnellbild.formatreader` / `.videodecoder`, profiles as secrets `MACOS_PROFILE_FORMATREADER` / `MACOS_PROFILE_VIDEODECODER` in the `release` environment; the profiles carry the Developer ID certificate that expires 2027-02-01 and must be generated again with a new one). Ad hoc with the entitlement: AMFI refuses it; without it: it starts, but is never asked.
- It is off until turned on in System Settings → General → Login Items & Extensions → Media Extensions; CI turns it on through the accessibility API (`ax-enable.swift`); `pluginkit -e use` doesn't.
- An app that calls `MTRegisterProfessionalVideoWorkflowFormatReaders()` gets it from AVFoundation.
- Quick Look thumbnails (`QLThumbnailGenerator`) use Media Extensions only when the asking process has opted in (`MTRegisterProfessionalVideoWorkflowFormatReaders()` and `VTRegisterProfessionalVideoWorkflowVideoDecoders()`, `Spike/MediaExtension/probe-me.swift`), and only on macOS 26: there QuickLook Video's extensions gave real MKV and WebM thumbnails and Quick Look asked our signed reader; on macOS 15 neither. A video-only AVI got none (AVFoundation reads that container itself; its codec needs a decoder).
- AVCHD (`.mts`, `.m2ts`, H.264 in 192-byte transport stream packets): AVFoundation opens it itself (opted in or not; 1.88 s for the fixture, where our reader says 2.00 s), but Quick Look's thumbnails of it on macOS 26 come only through our reader: with it on, a picture (the fixture 0.05 s; a real Canon HG10 1080/50i clip from samples.ffmpeg.org, 512×288 in 0.33 s, fields and 16:9 right); with the type claimed and the file refused by the reader, with it off, or for a process that doesn't opt in, none. On macOS 15 none either way. On the dev Mac (macOS 27, no reader installed) none, opted in or not. An x264-made interlaced test clip decodes with wrong colours in places through VideoToolbox, through our reader and through AVFoundation from an MP4 remux alike; the real camcorder clip doesn't.
- Schnellbild's own reader works: `Spike/MediaExtension/MKVParser.swift` (Matroska in plain Swift: tracks, codec setup, where each frame lies, bounds-checked) and `Reader.swift` (the MediaExtension classes; frames located with `sampleLocation`, decoded by macOS) gave AVFoundation frames on macOS 15 and 26, and a Quick Look thumbnail of an H.264 MKV on macOS 26 (0.8 s first, then from the cache), Developer ID signed with the profile, turned on, the asking process opted in. Open for the product: reading the file in parts instead of whole, hostile-file tests, VP9 and other codecs need a decoder.

Where the leads came from (QuickLook Video by Marginal, which moved to Media Extensions in its version 3):
- The asking app must opt in itself — `MTRegisterProfessionalVideoWorkflowFormatReaders` and `VTRegisterProfessionalVideoWorkflowVideoDecoders` — for Quick Look thumbnails to use Media Extensions (Finder does; ForkLift did from 4.7): https://github.com/Marginal/QuickLookVideo/issues/191, https://github.com/Marginal/QuickLookVideo/issues/197
- The thumbnailing process sometimes sees the extensions but doesn't use them (a macOS bug in the maintainer's words); its "Refresh" (`qlmanage -r cache`, killing `AudiovisualThumbnailExtension` and the extensions, Finder) helps: https://github.com/Marginal/QuickLookVideo/issues/172, https://github.com/Marginal/QuickLookVideo/issues/173, commit https://github.com/Marginal/QuickLookVideo/commit/107f71307f96e0b14e37edaad3f4f76231c7dcea
- Thumbnails need the video decoder too, and VideoToolbox hardware decoding (`VTIsHardwareDecodeSupported(kCMVideoCodecType_HEVC)`; virtual machines may lack it): commit https://github.com/Marginal/QuickLookVideo/commit/0835ef7
- Its exported types conform to `public.movie`, not `com.apple.mediaextension-content` (else the CoreMedia importer takes them): `formatreader/Info.plist` in that repo.
- A video-only AVI is read by AVFoundation itself, so the reader isn't asked; then only a decoder for its FourCC helps: https://github.com/Marginal/QuickLookVideo/issues/203
